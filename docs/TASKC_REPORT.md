## 1. 구조 — `tb-radio2.sh` v2 정독 (`.43:/usr/local/sbin/`)

```
ogstun root: HTB (default 9999 = 무제한)
  코호트 i (i=1,2), DIVISOR=64:
    class 1:(i*0x1000 + b)  htb rate 10000mbit   <- 무제한, 분류 컨테이너
      qdisc netem rate <밴드>                     <- 실제 셰이핑, 버킷마다 독립
  filter: dst IP로 코호트 분류 -> u32 hashkey mask 0x3f at 20 = dst 포트 하위 6비트
```

- 셰이핑 지점이 ogstun **egress**(하향)이라 커넥션 식별자는 **dst 포트**
  (UE의 ephemeral 포트)다. 커넥션 수명 내내 고정된다.
- **의도한 모형**: "커넥션 1개 = 가상 사용자 1명 = 자기 무선 링크 1개."
  커넥션당 요구량 0.317 Mbit/s이므로 극단 1,600 kbit에서 rho=0.20 —
  대기시간이 무시되고 `d_acc`가 §0.3 직렬화 값으로 남는다는 것이 설계 전제다.
- **실제**: 16개가 64칸에 들어간다. 충돌쌍 기대값 = C(16,2)/64 = **1.875쌍**
  (관여 커넥션 ~3.75개). 충돌하면 **두 커넥션이 netem 하나를 공유**하므로
  rho가 0.20 → 0.40이 되고 전제가 깨진다. **이건 설계가 아니라 버그다.**

## 2. 검증 — 네 단계 모두 통과

### 2.1 짝 검출 (시간 상관)

"A가 느려지는 것은 B가 큰 응답(search)을 전송 중일 때뿐인가?"를
쌍마다 양방향으로 계산하고, 둘 중 작은 값을 **대칭 리프트**로 썼다.

T8(radio, strict_far) — 가장 깨끗한 사례. 열화 커넥션 4개:

| 쌍 | A 위반 (B 전송중 / 아닐 때) | B 위반 (A 전송중 / 아닐 때) | 대칭 리프트 |
|---|---|---|---|
| c2–c4 | 50.0 % / **0.0 %** | 50.0 % / **0.1 %** | **+50.0 %p** |
| c1–c15 | 66.6 % / 17.0 % | 50.7 % / 0.9 % | **+49.6 %p** |
| (중앙값 쌍) | – | – | −0.1 %p |

**c2와 c4는 상대가 전송 중일 때만 위반하고 아닐 때는 정확히 0 %다.**
리프트 행렬에서 c2–c15, c4–c15는 −50 %p대(상호 배타)로 나와,
`{c2,c4}`와 `{c1,c15}` **두 쌍**으로 깔끔하게 갈린다 — 기대값 1.875쌍과 일치.

### 2.2 대조군 — 밴드가 없으면 구조가 사라진다

| 대조 | 최대 위반율 | 최대 대칭 리프트 |
|---|---|---|
| T8 c1, pre 구간 (밴드 주입 전) | 0.1 % | **+0.0 %p** |
| T10 c1, pre 구간 (밴드 주입 전) | 0.2 % | +0.2 %p |
| T10 c2, c1단독 창 (c2는 밴드 미적용) | 0.4 % | +0.3 %p |
| T11 c2, c1단독 창 (c2는 밴드 미적용) | 0.1 % | +0.0 %p |

밴드가 걸린 코호트에서만 +50 %p가 나오고, 안 걸리면 배경(+0.0~0.3 %p)이다.
**버킷이 존재할 때만 나타나는 현상**이라는 것이 확정됐다.

### 2.3 런 내 지속성 — 완전하다

교란 창을 전/후반으로 갈랐을 때 열화 집합이 **세 런 모두 완전히 동일**:

| 런 | 전반 | 후반 |
|---|---|---|
| T8 | {1, 2, 4, 15} | {1, 2, 4, 15} |
| T10 | {1, 2, 4, 8, 9} | {1, 2, 4, 8, 9} |
| T11 | {1, 3, 5, 7, 9, 10, 11, 13, 14} | {1, 3, 5, 7, 9, 10, 11, 13, 14} |

포트가 커넥션 수명 내내 고정이므로 버킷 배정도 고정이라는 예측 그대로다.
**→ 런내 시간분할 페어링(C-γ 후보 2)의 전제가 성립한다** (§5).

## 4. ★ 작업 A "주 결과 2"의 철회

개정 2 §3은 c1 단독 극단의 5.87 % vs 22.38 %를 주 결과로 올리면서,
"열화 커넥션 **개수**는 복권이지만 **피해 크기**는 복권이 아니다"라는 조건부
분해로 정당화했다. C0이 그 분해를 더 잘게 쪼갤 수 있게 해줬고, **결론이
뒤집혔다.**

### 4.1 충돌 없는 커넥션만 보면 차이가 사라지고 부호도 뒤집힌다

| c1 단독 극단 창 | T10 far_tier | T11 strict_far |
|---|---|---|
| **정상(비충돌) 커넥션만** | **0.83 %** (11개) | **0.50 %** (7개) |
| — recommend / reserve / search | 0.92 / 0.18 / 1.13 % | 0.47 / 0.37 / 0.62 % |
| 열화(충돌) 커넥션만 | 16.97 % (5개) | 39.40 % (9개) |
| 전체 (보고된 값) | 5.87 % | 22.38 % |

같은 반전이 radio 축에서도 나온다 — **정상 커넥션만**: T8 strict_far
**0.22 %** vs T9 far_tier **0.65 %**. 보고된 헤드라인(6.49 vs 1.18)과 정반대다.

**설계대로라면(충돌 0) 극단 밴드 창에서는 애초에 위반이 거의 안 나온다.**
rho=0.20이라 대기가 없고 search 22.4 ms 직렬화는 SLO 45 ms 안에 들어오기
때문이다. 보고했던 5.9 %와 22.4 %는 **둘 다 버그가 만든 값**이고, 그 격차는
"far_tier가 낫다"가 아니라 "T11이 충돌을 더 많이/더 나쁘게 뽑았다"를 뜻한다.

### 4.2 조건부 비교도 다중도가 안 맞았다

개정 2가 인용한 "열화 1개당 17.0 % vs 39.4 %(2.3배)"도 정확하지 않다.
리프트 행렬을 보면 **T11에는 3중 이상 충돌 그룹이 있다**(c11 55.7 %,
c13 73.5 %, c14 76.0 %). T10의 최대는 22.0 %로 2중 충돌 수준이다.
2중끼리만 맞춰 비교하면:

- T10 (5개): 13.5 / 15.9 / 16.7 / 16.7 / 22.0 → 평균 **17.0 %**
- T11 2중 부분집합 (5개): 22.2 / 23.3 / 23.4 / 24.1 / 24.3 → 평균 **23.5 %**

즉 **2.3배가 아니라 ~1.4배**다. 방향은 남지만 크기가 크게 줄고, 이 비교마저
"버그가 만든 혼잡 상태에서의 우열"이라 일반화가 어렵다.

## 5. C-γ (측정 프로토콜) — 사실상 해소 가능

§2.3에서 **열화 집합이 런 내내 완전히 고정**임을 확인했다. 따라서
**런내 시간분할 페어링이 성립한다** — 같은 런의 전반/후반에 정책을 바꾸면
버킷 배정(=복권)이 동일한 상태에서 정책만 비교된다. 코호트를 arm에
배정할 필요가 없으므로 지적하신 **코호트 비대칭 실험과의 충돌도 없다.**

단 두 가지를 확인해야 한다: (a) 정책 전환 후 과도구간 배제 폭,
(b) 전/후반 사이 드리프트(순서 효과) — 순서를 바꾼 반복으로 상쇄.

## 6. 새로 열린 질문 — 양 코호트 창의 붕괴 기전

작업 A §5는 양 코호트 창의 80~90 % 붕괴를 "커넥션 큐를 search 직렬화가
채운다"로 설명했다. **버킷 구조를 알고 나니 이 설명이 성립하지 않는다** —
커넥션마다 독립 netem이고 rho=0.20이면 큐가 안 찬다. 그런데 그 창에서는
**충돌과 무관하게 32개 커넥션 전부가 64~100 % 위반**한다. 즉 버킷보다
상위의 공유 병목(ogstun/GTP/UE 스택/gNB 또는 호스트 자원)이 지배한다는
뜻이고, 그게 무엇인지는 아직 모른다.
"access 병목 지배"라는 §5의 **결론 자체는 유지**되지만(사이트 선택과 무관),
**지목한 기전은 틀렸다.** C1에서 확인한다.

## 10. 적용한 수정

**생성기 소스 포트 고정.** `tb-load.py:_new_conn` 에 `local_port` 를 넣고
`--port-base` 로 받는다. 커넥션 i 는 `base+i` 를 바인드하므로 연속 16개
포트의 하위 6비트가 전부 달라 **버킷 충돌이 결정적으로 0** 이다.
`tb-radio2.sh` 는 건드리지 않았다.

- **TIME_WAIT 대응 = 런마다 BASE 회전** (`SO_REUSEADDR` 은 커널/상황에 따라
  거동이 갈려 쓰지 않는다). 회전 폭은 **64의 배수**여야 어느 런에서든 16개가
  서로 다른 버킷에 떨어진다 — `run_all.py:port_base_for_run()` 이
  `20032~31552` 를 64 단위로 돈다(ephemeral 32768~ 아래).
- **런 중 재연결도 버킷을 유지한다**: 바인드 실패 시 포트를 **64씩** 올려
  재시도한다(`PORT_LADDER_TRIES=24`). 64의 배수를 더하면 하위 6비트가
  보존되므로 같은 버킷에 남는다. 사다리를 다 쓰면 **조용히 포트 0 으로
  떨어지지 않고 런을 실패시킨다** — 복권이 되살아나는 것을 막기 위해서다.
- `TB_RADIO_DIVISOR` 상향은 채택하지 않았다. u32 divisor 상한 256 이라
  기대 충돌쌍을 0.47 로 낮출 뿐 **0 을 보장하지 못한다.** 결정적 보장이
  있는데 확률적 완화를 택할 이유가 없다.

## 11. 자동 검사 (`run_all.py:probe_buckets`)

이번 사고는 **설계 전제가 조용히 깨져 있던** 부류라 `check_netem_binding()`
과 같은 이유로 자동 검사가 필요하다. 교란 창 **중앙**에서 세 가지를 실측해
`postcheck` 에 합류시킨다 (실패 → 그 런만 SUSPECT).

1. **실제 소스 포트** — `.12` 에서 `ss -tn state established`. 커넥션 수·
   distinct 포트 수·distinct 버킷 수를 센다.
2. **버킷 점유 실측** — `.43` 에서 `tc -s class show dev ogstun` 의 클래스별
   패킷 카운터. **밴드가 걸린 코호트의 활성 버킷 수 == 커넥션 수** 여야 한다.
   산술로 추론하지 않는다. (파서가 빈 결과를 내면 조용히 통과하므로,
   밴드 걸린 코호트가 출력에 아예 없으면 그것부터 실패시킨다.)
3. **생성기 자경보** — `tb-load.py` 가 찍는 `PORT_BUCKET_WARN` 을 런 로그에서
   찾아 합류.

추가로 같은 시점에 **진단 스냅샷**(ogstun qdisc 통계·`ip -s link`·loadavg·
vmstat·top)을 `bucket_probe.txt` 에 남긴다 — §6 의 미규명 상위 병목 후보를
좁히기 위해서다.

## 13. ★ 남은 붕괴의 정체 — 규명됐다 (§6 종결)

§6 에서 "버킷보다 상위의 공유 병목, 정체 미상"으로 남겼던 것을 사이트별로
갈라 규명했다 (`analysis/taskC/c1_bottleneck.py`, request_id 조인, 실패 0건).

**양 코호트 창, 서비스시간(자기 지연) vs 보정시간(줄서기 포함):**

| C1a far_tier | SLO | svc p95 | 여유 | 위반(svc) | 위반(cor) |
|---|---|---|---|---|---|
| S1/search (266.9 rps) | 45 | **91.6** | **−46.6** | **92.18 %** | 94.67 % |
| S2/recommend | 35 | 18.6 | **+16.4** | 0.01 % | 67.36 % |
| S2/reserve | 35 | 18.2 | +16.8 | 0.02 % | 27.09 % |
| S3/recommend | 35 | 28.3 | **+6.7** | 0.01 % | 86.46 % |
| S3/reserve | 35 | 27.8 | +7.2 | 0.00 % | 42.07 % |

| C1b strict_far | SLO | svc p95 | 여유 | 위반(svc) | 위반(cor) |
|---|---|---|---|---|---|
| S1/search (266.2 rps) | 45 | 92.4 | −47.4 | 88.96 % | 98.50 % |
| S3/recommend (355 rps) | 35 | 28.3 | +6.7 | 0.03 % | 97.28 % |
| S3/reserve (177 rps) | 35 | 27.9 | +7.1 | 0.02 % | 87.59 % |

**기전은 두 단계다:**

1. **S1 포화.** 양 코호트 search 가 전부 `{S1}` 로 가 **266 rps** 가 되고,
   S1 은 감당 못 한다 — `service_ms` p95 가 33.0 ms(c1 단독 창, 133 rps)에서
   **92 ms** 로 뛰고 **자기 지연만으로 89~92 % 가 위반**한다. 순수 서버측
   포화다.
2. **커넥션 head-of-line 블로킹.** reserve/recommend 는 **자기 지연으로는
   사실상 절대 안 늦는다 (위반 0.00~0.03 %)**. 그런데 보정시간으로는
   27~97 % 위반한다. 생성기가 커넥션당 요청 1건만 in-flight 로 돌리므로
   (HTTP/1.1 직렬화) **같은 커넥션에서 앞선 S1 search 가 92 ms 씩 잡아먹는
   동안 뒤의 reserve/recommend 가 스케줄에 밀린다.**

### 13.1 작업 A §5 의 진단은 틀렸다

§5 는 이 붕괴를 "사이트 선택과 무관한 **접속 병목** 지배 / 라우팅으로 풀 수
없다"로 서술했다. **틀렸다.**

- 병목은 무선 구간이 아니다. **S1 이라는 특정 사이트의 용량**이다.
- S2·S3 는 놀고 있었다 — `svc p95` 18.6 / 28.3 ms 로 SLO 35 안에 여유롭게
  들어온다. 위반은 전부 S1 뒤에 줄 선 결과다.
- 따라서 **라우팅(용량 인지 배정)으로 풀 수 있는 문제다.**

### 13.2 정책 격차도 같은 기전으로 설명된다

충돌이 0 인 상태의 far_tier 73.3 % vs strict_far 95.3 % 는 **큐잉 여유의
차이**다. HOL 블로킹은 모든 클래스에 같은 양의 지연을 얹는데, SLO 까지의
여유가 다르다:

- far_tier 는 reserve/recommend 를 **S2(여유 16.4 ms)와 S3(6.7 ms)에 나눠
  싣는다** → S2 몫은 큐잉을 견딘다 (recommend 67.4 %).
- strict_far 는 **전량 S3(여유 6.7 ms)** 에 싣는다 → 거의 다 넘어간다
  (recommend 97.3 %). during 분배 실측 S2 0.0 % / S3 75.1 %.

여유 차 16.4 − 6.7 = **9.7 ms 는 `d_net`(S2 15 / S3 25) 격차 10 ms 그
자체**다. 개정 2 §3 이 주장했던 기전은 **옳았고, 근거로 든 창이 틀렸던
것**이다. 이제 그 기전이 양 코호트 창에서 깨끗하게 측정된다.

**단, 승격하지 않는다 — 정책당 n=1 이다.** 개정 2 의 교훈(ISSUES.md I-8
방법론 항목)을 그대로 적용한다. 반복 n≥3 후에 판단한다.

## 14. 작업 B 에 주는 것

- **갈래 1(사이트 용량 제약)이 정확히 이 문제를 푼다.** 결정식이 "S1 이
  266 rps 를 감당 못 한다"를 알면 초과분을 S2 로 넘긴다. 넘긴 search 는
  SLO 를 근소하게(≈46 ms) 넘기지만 **S1 이 안 무너지므로 잔류 search 가
  살고, HOL 블로킹이 사라져 reserve/recommend 가 전부 산다.**
  실측 기반 개략 추정: 전체 위반 **73.3 % → ≈8.6 %**.
  (가정: S1 한계 ~200 rps, 잔류 search 위반 ~1 %, reserve/recommend ~0 %.
  S1 무릎은 133 rps 정상 / 266 rps 포화 사이로만 좁혀져 있어 **실측 필요**.)
- **갈래 2(접속 병목 인정)의 전제는 약해졌다.** 무선이 무너져서 어디로
  보내도 실패하는 상황이 아니었다 — S2·S3 는 여유가 있었다. `EXPECTANT`
  100 % 는 여전히 참인 신호지만(모든 사이트 slack<0), 그 위의 올바른 행동은
  "포기/강등"이 아니라 **용량 인지 배정**이다. 갈래 2 는 재정의하거나
  우선순위를 낮춰야 한다.
- **before 기준선 갱신**: 작업 B 의 before 는 이제 T10/T11(80.9/87.3 %)이
  아니라 **C1a/C1b(73.3/95.3 %)** 다. T10/T11 은 충돌에 오염돼 있다.

## 15. 한계

- **HOL 블로킹은 생성기 모형의 성질이기도 하다.** 커넥션당 1건 in-flight +
  절대 스케줄이라, 앞 요청이 늦으면 뒤가 밀린다. 커넥션을 더 쓰거나
  HTTP/2 를 쓰는 클라이언트면 전파가 약할 것이다. 다만 (a) 실제 사용자도
  커넥션을 재사용하고 (b) CO 보정 지연이 사용자 체감에 정직한 지표이므로
  버릴 관측은 아니다. **논문에 쓸 때 이 조건을 명시해야 한다.**
- 정책 비교는 **정책당 n=1**. §13.2 는 기전까지 확인됐지만 승격 대상이 아니다.
- S1 용량 무릎이 미측정(133~266 rps 사이).
- C-γ(런내 페어링)는 **우선순위를 낮춘다** — 복권이 사라져 런 간 비교가
  가능해졌으므로 보험으로만 남긴다.
