## 2. `obs.py` — 인터페이스 · 내부 상태 · 파라미터

### 2.1 공개 인터페이스

```python
obs.init(cfg, **kw)                  # 싱글턴 생성 (cfg = sorts.yaml 로드 결과)
obs.update(now=None) -> float        # 주기당 1회. 반환 = 소요 [ms]
obs.get_resp_size(cls)   -> float    # bytes
obs.get_site_state(site, cls) -> float   # f_c, ms
obs.snapshot()          -> dict      # 진단 (decisions.csv 열 / 보고용)
```

지시 §2.1 의 격리 경계는 조회 2함수다. `init`/`update` 는 생명주기, `snapshot`
은 진단이다 — tail 기반이라 조회 함수만으로는 구성이 안 된다.
**프라이어 상수를 코드에 박지 않았다.** 전부 `cfg` 에서 온다.

### 2.2 내부 상태

- `w_bytes` : 클래스별 시간윈도 3개 (통계량 = **평균**)
- `w_fc` : 사이트×클래스 시간윈도 9개 (통계량 = **p95**)
- 코호트 구분 없음 — 6유닛 관측을 같은 9칸에 합산 (지시대로 코호트 맵 미사용)
- tail 위치 `(_ino, _offset, _partial)` + 부분 줄 이월
- `_cache_bytes`/`_cache_fc` : 주기당 1회 갱신, 조회는 O(1)
- 각 캐시 항목은 `n / mean / p95 / stale_ms / src / value / prior` 를 **모두** 보유
  → **평균·p95 둘 다 기록**(D3). 결정에 쓰는 것은 `value`(=p95)

### 2.3 파라미터 기본값과 근거

| 파라미터 | 값 | 근거 |
|---|---|---|
| `WINDOW_S` | 2.0 s | 지시값. 스무딩 파라미터는 이것 **하나뿐**(α 없음) |
| `N_MIN_FC` | 100 | 지시값. p95 를 100 표본으로 = 상위 5개 중 선택 |
| `N_MIN_BYTES` | 20 | 평균이라 표본이 덜 필요 |
| `STALE_TTL_S` | 2.0 | 지시값. 초과 시 **프라이어 복귀**(임의 페널티 없음) |
| `FC_QUANTILE` | 0.95 | D3. 프라이어가 무부하 service p95 라 축을 맞춤 |
| `MAX_READ_BYTES` | 8 MB | 280 KB/s 기준 30초 밀림 흡수. 밀리면 `backlog_bytes` 로 노출 |

분위수 관례는 `run_all.py:286` 과 동일(`sorted[round(q*(n-1))]`) — 기존 분석과 축을 맞췄다.

### 2.4 D1 필터 구현 (게이트 아님을 코드로 분리)

|---:|---:|---:|---:|
| 78 | 4.250 | **8.396** | 0.839 |
| 79 | 4.328 | **8.748** | 0.857 |
| **80** | **8.396** | 4.337 | 0.998 |
| **81** | **8.748** | 4.423 | 1.000 |
| 82 | 4.337 | 4.365 | 0.946 |

t≈78~79 의 실제 스파이크가 **2 tick 늦게** 추정에 나타나고, 그때는 이미 회복돼 있다.
윈도 2.0 s / 주기 1.0 s 이므로 스파이크는 윈도에 2 tick 머문다 — **구조적 지연**이다.
그 2 tick 동안 cov_fwd 가 1.0 (과보수)이고, 밴드 4500 이었다면 S3 를 2 초간 불필요하게
버렸을 것이다. 지시서가 예상한 "감지 지연과 경계 지터"가 이것이다.
윈도를 줄이면 지연이 줄지만 p95 표본이 준다 — 정면 trade-off라 D5(A) 범위를 넘는다.

**사건 B — 웜업 오염 (D6 t=1.0 s, S3 reserve, 전 밴드)**

| t_rel | n | mean | p95(=추정) | 실현 p95 |
|---:|---:|---:|---:|---:|
| 1.0 | 176 | 9.898 | **55.558** | 1.119 |
| 2.0 | 353 | 5.228 | 1.672 | 1.081 |
| 3.0 | 358 | 0.874 | 1.119 | 1.324 |

런 첫 1초의 연결 수립·콜드 캐시 꼬리가 p95 를 55.6 ms 로 밀어올린다(실제는 1.1 ms).
`n_min_fc=100` 은 176 으로 **통과**해버린다 — 표본 수는 충분한데 **윈도가 아직 안 찼다**
(1.0 s < WINDOW_S 2.0 s). 다른 5 슬라이스의 같은 tick 은 2.067/2.744/2.300 이라
임계(≈4.98 ms) 아래여서 안 뒤집혔다. D6 만 넘었다.
전환 표(§7)의 `+54.210 ms` 계단이 같은 사건이다.

**제안(미구현, 승인 필요)**: `_Window` 에 첫 표본 시각을 두고
`last_ts − first_ts >= 0.8×WINDOW_S` 일 때만 obs 로 전환하는 **윈도 충전 게이트**.
사건 B 를 정확히 제거하고 사건 A 에는 영향이 없다. 파라미터 추가가 아니라
기존 `WINDOW_S` 의 종속값이라 D5(A) 정신에 어긋나지 않는다고 판단하지만,
거동 변경이므로 **Phase 1 범위에서 넣지 않았다.**

## 8. 주기당 소요 시간 (지시 §3.6)

리플레이의 `update()` 로는 이 값을 못 잰다 — `log_path=None` 이라 tail 이 없고
ingest 는 줄 단위로 `update()` 바깥에서 돈다. 그래서 **`obs_tail_bench.py` 를 추가**해
아카이브 슬라이스를 실제 파일에 덧붙이며 Observer 가 그 파일을 tail 하게 했다
(= 라이브와 같은 경로: stat→seek→read→decode→split→ingest→prune→분위수).

D6 슬라이스(33.6만 줄, 800 lines/s), `.40` 기준:

| 주기 [s] | ticks | p50 [ms] | p95 [ms] | p99 [ms] | max [ms] | duty % | 여유배수 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1.000 | 420 | 3.328 | 3.380 | 3.423 | 10.104 | 0.33 | 296× |
| 0.100 | 4200 | 0.726 | 0.754 | 0.765 | 0.823 | 0.73 | 133× |
| 0.050 | 8400 | 0.585 | 0.612 | 0.623 | 7.346 | 1.18 | 82× |
| 0.025 | 16800 | 0.521 | 0.552 | 0.566 | 7.515 | 2.09 | **45×** |

**작업 2 결론(잠정)**: 주기를 25 ms 로 내려도 p95 0.55 ms, duty 2.1 %, 여유 45 배다.
관측 계층은 주기 하향의 병목이 아니다. 고정비 바닥은 ~0.52 ms(윈도 12칸 prune+분위수)
이고 읽기량은 주기에 비례해 줄어 총 CPU 는 거의 불변이다.

참고로 리플레이의 recompute-only 비용(표 7)은 p50 0.61~0.63 ms / max 1.11 ms 로
위 고정비와 일치한다.

> **한계**: 이 수치는 `.40` 기준이다. 컨트롤러는 `.43` 에서 돈다.
> 작업 2 확정 전 `.43` 에서 같은 벤치를 한 번 더 돌려야 한다 (사이트 복구 후).
>
> **R9(Envoy `--file-flush-interval-msec 100`) 심각도 하향 (Phase 2 회신)**:
> flush 지연 100 ms 는 윈도 2.0 s 의 5 % 라 `f_c` 추정에 무의미하다. 제약이
> 되는 것은 제어 주기 T 를 1 s 아래로 내릴 때뿐이다 — 작업 2 결정 항목으로만
> 남기고, 관측 계층의 리스크 목록에서는 낮춘다. (충전 게이트 적용 후 `.40`

**결함 2 — 벤치 최초판이 상대시각으로 tick 을 굴렸다 (수정 완료, obs.py 무관)**
로그 줄의 `START_TIME` 은 절대 epoch 인데 tick 을 상대초로 굴려 `prune` 의 cutoff 가
음수가 됐다 → **윈도가 하나도 안 버려지고** 33.6만 표본까지 자라 주기 비용이
**~72 ms** 로 측정됐다. 절대 시간축으로 고치니 3.3 ms. `obs.py` 는 라이브에서
`now=time.time()`, 리플레이에서 로그 ts 기반이라 둘 다 epoch 로 일치하므로
**이 버그는 벤치 하네스에만 있었다.**

두 결함 다 "측정 도구가 조용히 틀린 값을 낸다"는 같은 부류다. 표 7 은 재산출했다.
