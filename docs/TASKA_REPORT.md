## 3. 무선 축은 측정 무효 — 개정 2 "주 결과 2"의 철회

개정 2는 c1 단독 극단 창의 위반율(far_tier 5.87 % vs strict_far 22.38 %)을
주 결과로 올렸다. 근거는 "열화 커넥션 **개수**는 복권이지만 하나가 겪는
**피해 크기**는 복권이 아니다"라는 조건부 분해였다. **작업 C0이 복권의
기전을 규명하면서 이 분해가 무너졌다. 철회한다.**

### 3.1 기전 (요약 — 전문은 `TASKC_REPORT.md`)

`tb-radio2.sh` v2는 커넥션을 **dst 포트 하위 6비트로 64개 버킷**에 해싱하고
버킷마다 독립 netem을 매단다("커넥션 1개 = 가상 사용자 1명 = 자기 무선
링크 1개"). 그런데 커넥션이 16개뿐이라 **생일문제로 매 런 평균 1.9쌍이
같은 버킷 = 같은 netem 큐를 공유**한다. 공유한 두 커넥션은 서로의
4,474 B search 응답 뒤에서 기다린다. **설계 전제(rho=0.20, 대기 없음)가
깨지는 테스트베드 결함이다.**

검증(전부 read-only): 짝 대칭 리프트 +50 %p(T8 c2–c4는 상대 전송 중
50 % 위반, 아닐 때 0.0 %) vs 중앙값 쌍 −0.1 %p / 밴드 없는 구간·코호트
대조 +0.0~0.3 %p / 열화 집합은 런 내내 완전 고정.

## 4. I-9·I-10·클린 고부하 — 같은 결함의 세 발현 (한계 사이클의 이동)

**작업 A의 진짜 발견은 radio 축의 트레이드오프가 아니라, 진동이 사라진
게 아니라 한 칸 옮겨갔다는 것이다.** 그리고 2026-08-10 배치가 세 번째
발현을 추가했다 — **교란이 전혀 없어도** 부하만으로 같은 순환이 돈다.

세 발현은 별개 이슈가 아니라 **하나의 결함이 세 조건에서 발현된
것**이다. 결함 자체는 한 문장이다 — **결정이 자기 결정의 부하 효과를
모른다.** 관측판 `f_c`는 매 순간 옳지만, 그 관측은 *지금 내가 보낸
트래픽이 만든* 값이다. 그래서 어느 경계에 서 있든 같은 순환이 돈다:
여유가 있다고 판단 → 부하를 실음 → 관측 `f_c` 상승 → 여유 소진 →
집합 축소/이동 → 부하가 빠짐 → 식음 → 반복.

| | I-9 (Phase 4, strict_far) | I-10 (작업 A, far_tier) | 클린 고부하 (taskB-prep, strict_far) |
|---|---|---|---|
| 조건 | server 스트레스 | 무선 열화 후 엣지 개방 | **교란 0, 1400 rps 만** |
| 경계 | S3/S2 (원거리 티어 내부) | **S2/S1 (원거리↔엣지)** | S3/S2 |
| 발현 | `S2↔S3` 78전환, 듀티 33.9 % | `{S2}↔{S1}` **71전환**, 개방 15.7 % tick | `S3↔S2` **주기 2 (1 s)**, 유닛당 420전환/426틱, 6유닛 동조 |
| 부하를 실은 주체 | 외부 스트레서 + 단일 선택 | 집합 분배(평시 S2에 56 %) | **자기 결정 단독** (전량 단일 사이트) |
| 잠식되는 여유 | S3 slack | S2 slack +3.6 ms → 관측 `f_c` 음수화 | S3 예산 10.98 ms < 관측 `f_c` ~27 ms; 이동한 S2는 무릎(1000) 초과 **진짜 과부하**(slack −89~−103) |
| 유지 기전 | 부하 되먹임 | 부하 되먹임 | 부하 되먹임 + **stale_ttl 2 s** (떠난 사이트 관측 만료 → prior 복귀 → 재진입) |
| 피해 | 진폭 18 ms, 위반 0.89 % | **엣지가 열린다** — 개방 시 ~116 rps가 S1로 | **위반 ~70 %** (service 위반 20~51 % 실과부하 + HOL) |
| far_tier 효과 | 진폭 축소 (78→4전환) | 경계 이동 (자기 침식) | **어트랙터 소멸** — 700/700 분산, 전환 0, 위반 0.14~0.17 % (4/4런, 야간 포함 5/5) |
| 발생 양상 | 결정적 | 결정적 | ★**준안정** — 락인 3/7 (야간 포함 4/8); 락인 시 피해는 재현적(70.0~71.0 %), 락인 여부만 확률적. 발생률 유의성 미달(Fisher p≈0.24) — 트리거 통제 실험 제안(`analysis/taskB-prep/d1_repeat.md`) |

- **집합화가 한 일과 안 한 일**: 집합화는 S3/S2 경계에서 진폭을 크게
  줄였다(18.0→8.7 ms, 전환 78→4). 그 대가로 평시 S2 상재 부하가
  56 %로 올라갔고, 그만큼 **S2/S1 경계의 여유가 얇아졌다.** Poor 진입 시
  이 얇아진 여유가 먼저 무너진다. 즉 진동은 소멸한 것이 아니라 **여유가
  가장 얇은 경계로 이동**한다. 이것이 정직한 한 줄 — *허용 집합은 진동의
  위치를 바꾸고 진폭을 줄이지만 제거하지 않는다.*
- **I-10이 I-9보다 나쁜 이유**: `far_tier`의 존재 이유가 **엣지 보존**인데,
  그 정책이 만든 부하가 엣지를 열게 만든다. 정책이 자기 목적을 자기
  부하로 침식한다. strict_far(T8)는 c2를 S3에 뒀으므로 S2가 가벼워 같은
  조건에서 S2에 고정됐다 — 진동 없음. 여유를 안 썼기 때문에 안 무너진
  것이지, 제어가 더 나아서가 아니다.
- **그래서 작업 B는 선택이 아니라 필수다.** 히스테리시스나 최소 체류
  시간은 *증상*(전환 횟수)을 누른다. 근인은 결정이 부하 효과를 모른다는
  것이고, 그것을 아는 유일한 방법이 **용량을 결정식에 넣는 것**이다.
  같은 뿌리이므로 완화도 같은 곳에서 나온다.
- 참고 — T8/T9 절대 비교(6.49 % vs 1.18 %)는 **하지 마라 (I-8)**:
  커넥션별 위반율이 T8은 [12개×0.1~0.3 %, 7.4, 7.5, 7.9, 11.3 %], T9는
  [14개×0.1~0.4 %, 1.3, 3.1 %] — 런 단위 복권 추첨이 지배한다. 위 표에서
  인용하는 것은 **전환 횟수·개방 tick 비율·개방 시 유입 rps** 같은 구조
  지표이고, 이들은 결정 로그(decisions.csv) 기반이라 복권과 독립이다.
- 비개방 초의 S1 유입 1,129건은 전환 71회 × tick 1 s 경계 양자화다
  (전환당 ~16건). 결정-트래픽 조인의 해상도 한계로 기록해 둔다.

## 5.6. [개정 5] 서사 변경 — 변별은 무선이 아니라 용량 경계에서 나온다

> 우리 방법의 변별은 무선 자체가 아니라 **용량 경계**에서 나온다.
> 무선 관측은 필요조건이고, 용량 인지가 충분조건에 가깝다.

기존 서사("무선을 보는 것이 기여")를 이렇게 바꾼다: **"무선을 보되 용량을
알아야 그 관측이 결과로 이어진다."** 이것이 작업 B 가 선택이 아니라 논문의
핵심 절반인 이유다 — §4의 세 발현(결정이 자기 부하 효과를 모른다)과 §5.5의
RR/LR 역전(용량을 모르는 실행가능성 판정)이 같은 지점을 가리킨다.

용량 실측 입력(야간 과제 1 + taskB-prep 과제 A, S1 은 SLO 예산 기준):
search 단독 260 / 혼합(1:1.5:2) 500 / S2 혼합 1000 / S3 혼합 >1600.
용량은 조성 의존 — 가중 등가 부하 w=(search 1, reserve 0.278, recommend
0.178), C(S1)=279 (측정 조성 범위 안에서만; `analysis/taskB-prep/weight_estimation.md`).

### 작업 B는 두 갈래다

1. **사이트 용량 제약** — 집합 결정에 "사이트별 수용 가능 유입"을 넣는다.
   엣지 경합 시 누구에게 줄지(`B_eff` 오름차순 우선순위, `decide()`의
   [자리] 주석). before 기준선은 T10/T11 양 코호트 창(80.9 / 87.3 %).
   I-10의 S2/S1 경계 진동도 여기서 같이 완화된다 — §4대로 같은 뿌리다.
2. **접속 병목 인정** — 무선이 이만큼 무너지면 **어느 사이트로 보내도
   실패한다**는 것을 결정식이 알아야 한다. `EXPECTANT`가 이미 그 신호인데
   지금은 기록만 한다. 논문에서는 이쪽이 오히려 강한 주장이 될 수 있다:
   **"우리 방법의 유효 범위를 시스템이 스스로 안다."** 그 위에 무엇을
   할지(강등 / 부분 차단 / 클래스 우선순위)는 **별도 설계이며 지금
   정하지 않는다** — 작업 B 착수 시 옵션으로 제시한다.
