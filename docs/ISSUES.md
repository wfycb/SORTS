## I-1. `d_net(S1)=2.0 ms` — 캘리브레이션 페이로드(10 KB)와 실제 페이로드 불일치

**등록** 2026-08-06 (작업 1 Phase 0 조사)
**정정** 2026-08-07 — 원인 재규정. 구판("모델이 물리 181 µs와 안 맞는다")은
틀린 대조였다. 181 µs 는 d_net 이 아니라 **netem 주입값**이고, d_net 의 정의는
`tb-netem.sh`(.43) 주석에 있다:

```
주입값(i) = 목표 d_net(i) − 실측 기본 RTT(i, 10KB 페이로드)
2026-08-02 실측 (root, -i 0.01 -c 100, -s 10000):
  S1 avg 1.818 ms → 2 − 1.818 = 0.182 ms
S1 의 큰 기본 RTT 는 100 Mb/s 링크의 10KB 직렬화(왕복 약 1.6 ms)다.
```

즉 `d_net = netem 주입값 + 10 KB ping 왕복 실측`. 2.0 이라는 숫자 자체는
정당하게 만들어진 값이다.

**상태** 미해결 — **작업 6(반복 실험) 전에 결론 필요** (유지)

### 진짜 원인

**캘리브레이션 페이로드(10 KB)와 실제 응답 페이로드(36 B ~ 4474 B)의 불일치.**
S1(.3, sunny)은 **100 Mb/s 링크**(I-2)라 10 KB 왕복 직렬화 ~1.6 ms 가
d_net 2.0 에 포함돼 있다. 그런데 실제 응답은 전부 10 KB 보다 작아
직렬화 항이 응답 크기에 비례해 줄어들고, `f_c = 필드18 − d_net` 에서
그 차이만큼 **과다 차감**된다. 응답이 작은 엔드포인트일수록 심하다.

음수 비율이 이 구조를 정확히 따른다 (demo-20260805, 201만 요청):

| 셀 | 응답 크기 | 음수 비율 | f_c p50 |
|---|---|---|---|
| S1 recommend | 200 B | **56.42 %** | −0.177 |
| S1 reserve | 36 B | **46.48 %** | +0.099 |
| S1 search | 4474 B | 0.00 % | +5.366 |

S2/S3 에서 안 나타나는 이유: netem 주입값(14.7/24.7 ms)이 지배적이라
기저 RTT 의 페이로드 의존분(≤0.3 ms)이 무시할 수준이다. S1 만 주입값이
0.182 ms 라 직렬화 항이 그대로 드러난다.

재해석 후에도 남는 모순: 관측 업스트림 왕복(필드18) **하한 0.945 ms** 가
모델 d_net 2.0 보다 **1.055 ms 작다**. d_net 이 "왕복 실측"이어도 실제
트래픽의 최소 왕복보다 큰 값을 빼고 있다는 사실은 그대로다.

### 현재 라우팅에 미치는 영향: 없음 (근거 2개, 구판에서 유지)

1. **자기정합성.** 결정식이 더하는 `d_net` 과 관측기가 빼는 `d_net` 이 같은
   값이라 `d_net + f_c = 관측 RTT` 로 상쇄된다. `slack` 은 분할 오차와
   무관하게 정확하다. → `obs.py` 는 음수를 **클램프하지 않는다**.
2. **`site_order = [S3, S2, S1]` 이라 S1 은 항상 마지막.** S1 의 slack 부호는
   라우팅을 바꾸지 않고 `EXPECTANT` 플래그만 바꾼다.

영향 범위는 **논문에 f_c(S1) 절대값을 인용할 때**로 한정된다.

### 선택지 (구판 (A)/(B) 폐기)

**(C) d_net 을 엔드포인트별 실제 페이로드로 재캘리브레이션**

- 장점: f_c 가 순수 서버 시간에 가장 가깝다.
- 단점: d_net 이 엔드포인트별 상수가 되어 모델·코드가 복잡해진다.
  전체 재실행 필요(비교 가능성).

**(D) d_net 을 페이로드 무관 최소값(예: 64 B ping)으로 정의하고 직렬화는 f_c 에 남김**

- 장점: d_net 정의가 단순·안정("빈 경로 왕복"). 직렬화는 페이로드의
  함수이므로 서버 쪽 항에 두는 것이 물리적으로도 맞다.
- ★ **관측 기반 f_c(작업 1)로 가면 (D)는 사실상 공짜다.** 관측 f_c 는
  `필드18 − d_net` 실측이므로 직렬화가 관측값에 자연히 포함된다.
  프라이어 테이블만 한 번 재정의하면 된다.

### 결론: (D) 채택 — 실행은 작업 6 경계에서 (2026-08-07 확정)

**(D) 채택.** `d_net` 을 페이로드 무관 최소값으로 재정의하고 직렬화는 `f_c`
에 남긴다. 관측 기반 `f_c`(작업 1)가 직렬화를 자연 흡수하므로 사실상
공짜다. **단 지금 프라이어 테이블을 재정의하면 demo-20260805 와 비교가
깨지므로 실행은 작업 6 에서** — 그때까지 `obs.py` 는 음수 f_c 를 그대로
통과시킨다 (자기정합 상쇄).

부수 항목: `sorts.yaml` 은 `S3: 25.0`, `s6_calib.py`/`calib_stress.py` 는
`25.006` 을 쓴다. 6 µs 차이라 실질 영향은 없지만 값이 두 군데에 있다.

영향:

sunny 는 팀원 자산이라 NIC/스위치 교체는 우리 권한 밖이다.

## I-3. DHCP 리스 변경으로 사이트 IP가 바뀜 (2026-08-07)

- 증상: .2 → .10, .3 → .11 로 변경. 호스트는 정상이었음.
- 위험: netem u32 필터가 목적지 IP 하드코딩(c0a80002/03/28)이라
  새 주소는 필터에 안 걸림 → d_net 이 조용히 0. 무에러 실패.
- 조치: NM manual 고정으로 원주소 복구(DNS 는 DHCP 가 주던
  61.78.109.2/168.126.63.1 복제). precheck 에 tc 카운터 검증
  `check_netem_binding()` 추가 — ping N발 후 해당 밴드 class 카운터
  delta ≥ 0.9N 확인. RTT 임계는 쓰지 않는다(S1 은 주입 181 µs 라
  기저 LAN 지터와 마진이 없고, d_net 은 10 KB 실측이라 ping 임계
  기준으로도 부적합).
- **원인 확정(2026-08-07, Phase 4 지시)**: **공유기 교체**였다. 1회성
  사건이고 교체 예정이 없으므로 재발 위험은 크게 낮아졌다 → 위험도 하향.
- 잔존 위험(유지): **새 공유기의 DHCP 풀 범위는 미확인** → 새 기기가
  .2/.3 을 받아 충돌할 가능성은 원리적으로 남아 있다. 라우터
  (ipTIME 192.168.0.1, lighttpd/1.4.64) DHCP 예약 미적용. MAC:
  S2 b8:85:84:ad:e9:1a, S1 00:4e:01:a6:76:e4, GW b0:38:6c:94:29:67.
  여유 시 DHCP 풀 시작 주소 상향 + MAC 예약 권장. 관리자 비밀번호는 이
  저장소에 두지 않는다.
- **대응 축소(2026-08-07, Phase 4)**: 위험 하향에 따라 MAC
  precheck/postcheck 는 **구현하지 않기로** 했다(라우터 예약 대체안 폐기).
  대응은 `check_netem_binding()` **pre/post** 로 축소 — precheck(기존) +
  런 종료 시 `postcheck()`(run_all.py, 신설) 재확인. 어긋나면 그 런만
  SUSPECT 마커를 받고 배치는 계속한다. **탐지는 되나 예방은 아니다.**
  무인 실행(작업 6)에서 사고 피해를 런 1개로 제한하는 방어선이다.
- 미전환: .40/.43/.12 는 여전히 DHCP (`ipv4.method auto` 실측 확인).
  **`.43` 미전환 확정(2026-08-07)** — tc 초기화 위험이 이득보다 크다.
  precheck(`check_netem_binding`)이 잡아준다. **사고 재발 시 재검토.**
  전환하게 되면 직후 tc qdisc/filter/class 전수 확인 필요(nmcli con up 이
  tc 를 초기화할 가능성은 여전히 미검증).

## I-5. 응답 바이트는 예약 상태의 함수 — search 4474/4632 해명

**등록** 2026-08-07 (작업 2 조사)

### 실측 (2026-08-07)

- reset 전: S1=4474×5, S2=4632×5, S3=4632×5 (사이트별 완전 안정).
- reservation 문서수: **S1 39,112 / S2 0 / S3 0.**
- `reserve_reset.sh` 적용(재시작 없음 — drop + flush_all) 후:
  **세 사이트 모두 4632×5 수렴.** 문서수 전부 0.

### 결론

- **4632 = 예약 0 상태**(모든 호텔 가용), **4474 = 잔존 예약으로 검색
  결과에서 호텔이 빠진 상태.** 부하 mix 가 hotelId=1 만 예약하므로
  158 B 차이는 hotel 1 엔트리로 추정(추측 — 응답 diff 미확인).
- 아카이브의 4474 95~99% 는 런 중 예약이 빠르게 누적되어 정상.
  4632 는 reset 직후 잠깐 나오는 값이다.
- **런 밖 수동 측정으로 사이트 간 바이트를 비교하려면 reset 을 먼저
  돌려야 한다.** 러너는 이미 하고 있다 (`run_all.py` precheck 직후
  `reserve_reset.sh` 호출) — 문제였던 것은 수동 측정 쪽이다.

### 판정 관례 (의도적으로 다른 두 가지 — 통일하지 말 것)

- 러너 `is_valid()`: status 200 + `|bytes − EXPECT_BYTES| ≤ 10%`(>1000 B 만).
  4474/4632 둘 다 통과. 위반율 회계용.
- `obs.py`: 바이트를 게이트로 쓰지 않는다(순환 방지). `KNOWN_BYTES` 는
  카운터 전용.

### 잠재 위험 (지금 고치지 않는다)

`EXPECT_BYTES` 의 reserve(36)/recommend(200)는 `e ≤ 1000` 이라 **정확
일치**를 요구한다. 응답 크기가 1 B 라도 변하면(예: DSB 업데이트, 에러
메시지 변화) 해당 엔드포인트 전량이 위반으로 집계된다. 고치지 않는
이유: 집계 기준 변경은 demo-20260805 와의 비교를 깨므로, 바꾼다면
작업 6 재실행과 함께 바꿔야 한다.

10.093 ms)이 프라이어(6.899)로 낙관 점프하고, 그 낙관이 사이트를 다시
선택하게 만들면 관측이 재개되어 다시 버리는 진동 루프가 이론상 가능하다.

- **발현하지 않는 축**: 무선(radio). S3 를 버리는 원인이 d_acc(연속 관측,
  스테일 없음)이지 f_c 가 아니라서 루프의 트리거가 없다.
- **발현 예상 축**: server 교란 (S1 --cpu 1 --cpu-load 30 /
  S3 --cpu 2 --cpu-load 80, s6 캘리브레이션 완료 상태) — f_c 가 원인이
  되어 사이트를 버리는 유일한 축이다.
- **현 대응**: 설계 유지 + 계측만. `obs.py` 가 스테일 복귀 직전 마지막 관측
  p95 를 `last_obs` 로 유지하고 `obs_state.csv` 의 `last_obs_ms` 열에
  남긴다. Phase 4 server 축에서 진동이 실측되면 그때 판단한다.
- **대안 2개** (미구현): ① 감쇠 복귀 — 프라이어로 즉시 점프하지 않고
  last_obs 에서 프라이어로 시간 감쇠. ② 버린 사이트 소량 프로빙 —
  트래픽의 ε 를 계속 보내 관측을 유지 (Prequal 류). 둘 다 파라미터가
  늘어나므로 실측 근거 없이 넣지 않는다.
- 부수: 충전 게이트(Phase 2)가 복귀 시점을 1 tick 당긴다 — 트래픽이 마르면
  스테일 판정 전에 윈도 폭이 먼저 얇아져 prior_fill 로 넘어간다. 이때

  신판에서 +0.421(t=361) + 0.000(t=362) 으로 분해).

  (+0.60) **이후**라 발표 수치는 보수적이다(정정 불필요). 표 4 의 "+0.328 s"도
  기준이 `t43_done`(+0.866)이라 t_issue 기준 +1.19 s.
- **영향 받는 것**: 주기 ablation(2단계). T=50/25 ms 면 감지가 항상 A1 직후
  (0.26~0.31 s) = 발효 이전이라, "burst 위반 감소"가 아직 시작되지 않은 위반의
  회피로 계상된다 — 인공물. 현 주입 primitive 위에서 T ablation 불성립.
- **대응 후보(미실행)**: ① 주입 primitive 를 "트리 선구축 + rate 만 교체" 로
  바꿔 가시화≈발효로 붙임(권고, radio 축 절대 반응시각의 계열 비교는 포기)
  ② 기준점을 발효 시각으로 변경(인공물 잔존) ③ 관측을 측정 기반으로 전환
  (설계·논문 전제 변경).
- 부수: 앵커 이탈(0.305 vs 1.08~1.14)의 원인은 코드·arm 이 아니라 **tick 위상
  양자화**로 규명됐다 — `감지 = leaf 가시화(0.26 s) 지난 첫 tick` 규칙이 7런을
  정확히 예측. P-S2-0 은 T 로 양자화되고 경계에 인접해 회귀 앵커로 부적격.

## I-18. [운영 함정, I-15 계열] 조용한 무효화 2종 — sudo env 스트립 / str.replace 미적용 (2026-08-12, STAGE3)

## I-20. `d_acc` 모델이 본문 바이트만 계상 — 작은 응답에서 낙관적 (2026-08-13, graph-data)

**등록** 2026-08-13 (지도교수 회신 대응 분해 추출 중 부수 발견)
**상태** 등록만 — **결정 로직 수정하지 않음**(동결 유지). 근거는 아래 §3.

### 증상

결정식이 쓰는 접속 지연 추정 `d_acc = 응답본문바이트 × 8 / rate × 1.10`
(`sorts.yaml` 의 `resp_bytes` + `overhead`)이 1600 kbit 인가 시의 **실측
무선 구간 증분**과 클래스별로 크게 어긋난다.

| 클래스 | 본문 | 모델 `d_acc` | 실측 증분 | 오차 |
|---|---|---|---|---|
| search | 4474 B | 24.61 ms | **24.82 ms** | **−0.8 %** |
| recommend | 200 B | 1.10 ms | **2.25 ms** | **−51.2 %** |
| reserve | 36 B | 0.20 ms | **1.43 ms** | **−86.1 %** |

실측 증분 = `p50(degraded) − p50(normal)` 의 무선 구간(= `service_ms` −
Envoy 필드16), L450 3정책 풀링. 출처 `figures/data/prof/G1b_model_vs_measured.csv`.

### 원인 — HTTP 응답 헤더 + IP/TCP 헤더 미계상

netem 의 `rate` 는 **패킷마다 `len × 8 / rate` 를 더하는 직렬화 모형**이라
IP 패킷 전체 바이트를 센다. 모델은 HTTP 응답 본문만 센다.

단일 패킷 클래스(reserve·recommend)의 함의 바이트에서 프레임 오버헤드를
적합하면 **`H_http` ≈ 210 B**(+ 패킷당 IP/TCP 40 B)가 나오고, 이것을 search
로 외삽하면(4474 + 210 → 4 패킷 → 4844 B) **오차 −2.4 %** 로 재현된다.
즉 진단이 맞다. reserve/recommend 의 보정 후 오차(+0.1 / −0.1 %)는 적합점이라
검산이 아니고, **독립 검증은 search 한 클래스뿐**이다.

`1.10` 이라는 오버헤드 계수가 search 에서만 잘 맞는 이유도 같다 — 4474 B 의
10 % = 447 B 가 우연히 실제 헤더 오버헤드(210 + 160 = 370 B)와 비슷하다.
본문이 작아지면 이 비례 보정이 고정 오버헤드를 못 덮는다.

### 결정 품질에 미치는 영향: 없음 (수정하지 않는 이유)

1. **SLO 를 지배하는 클래스에서 정확하다.** 1600 kbit 에서 예산이 좁아져
   실제로 변별이 일어나는 칸은 search 뿐이다(예산 표
   `analysis/stage6/budget_table.csv`: search@1600 k → S1 +13.4 / S2 +0.4 /
   S3 −9.6 ms). 그 클래스의 오차가 **0.8 %** 다.
2. **작은 응답 클래스는 예산이 압도적으로 남는다.** reserve/recommend 의
   `d_acc` 오차 절대값은 각각 1.2 / 1.2 ms 인데, 같은 밴드에서 예산은
   최소 3.9 ms(S3 recommend) ~ 27.8 ms(S1 reserve)다. 1.2 ms 를 더 빼도
   feasible 판정이 뒤집히는 칸이 없다.
3. **동결**. 결정 로직 6파일은 `b3-freeze` 이후 md5 불변이고 해제 창은
   전부 닫혀 있다(`docs/FREEZE.md`). 판정을 바꾸지 않는 오차를 위해 전
   실험을 재실행할 이유가 없다.

### 재검토 조건

- 새 클래스(응답 본문 < 1 KB)에서 예산이 **2 ms 미만**으로 좁아지는 조건이
  생기면 재검토. 그때는 `d_acc` 를 `(B + 210 + 40×⌈(B+210)/1360⌉) × 8 / rate`
  로 바꾸는 것이 최소 변경이다(`overhead` 계수는 제거).
- 응답 크기나 MTU(현 ogstun 1400)가 바뀌면 `H_http` 적합값을 다시 재야 한다.
