# 알려진 한계 (P5.3)

각 항목의 **영향 방향**: `낙관` = 결과를 실제보다 좋게 보이게 함,
`비관` = 나쁘게 보이게 함, `중립` = 방향을 특정할 수 없거나 상쇄됨.

## 1. 관측 함수가 에뮬레이터 설정값을 읽는다 — **낙관**

`get_access_state()` 는 ogstun 의 tc 에 **설정된** achievable rate 를 읽는다
(`sorts_ctl.py:read_rates`).

- 실측 처리량이 아니다. 링크 이용률 ρ≈0.2 라 실측 처리량은 모든 밴드에서
  거의 같아 밴드를 구분할 수 없고, gNB 가 CQI/MCS 로부터 보고하는 것도 이용량이
  아니라 달성 가능 대역이므로 **모형상 이 선택이 맞다.**
- 그러나 이 관측에는 **측정 노이즈도 보고 지연도 없다.** 실제 RAN 에서는 둘 다
  존재하며 그만큼 반응이 늦어진다.
- 관측 지연은 제어 주기 `T_ctrl` = 1 s 에서만 발생한다. 이번 런에서 감지 지연은
  0.328 s 였다(주입 시각과 제어 주기의 위상차).

**방향: 낙관.** 표 4 의 잔여 위반(44건, during 의 84.6%)은 **하한**이다.
노이즈·보고 지연이 들어가면 잔여 위반은 늘어난다.

## 2. 반복 n=1 — **중립**

데모 6런은 각 조건 1회다. 통계가 아니라 작동 확인이 목적이었다.

지금 낼 수 있는 유일한 오차 지표는 `d1-20260804` 배치의 반복 편차다.
같은 정책이 4번 등장하고 각 런의 pre 구간은 교란 전이다.

| 기준 | 변동계수(CV) 중앙값 | 최대 |
| --- | ---: | ---: |
| 4런 전부 | 2.00% | 29.94% |
| **3런 (B_ramp 제외)** | **0.40%** | **2.37%** |
| 3런, bl_loc(포화) 제외 | 0.32% | 1.34% |

B_ramp 를 빼는 이유: 그 런의 pre 창에는 `ramp_base` 20 Mbit/s 셰이핑이 걸려 있어
조건이 같지 않다(defects #14). 29.94% 는 그 오염의 산물이다.

**해석**: 비포화 조건에서 런 간 편차는 **CV 0.3~1.3%** 수준이다. 표 1 의
정책 간 차이(0.34% vs 22.8% vs 33.5% vs 100%)는 이 편차보다 훨씬 크다.
다만 이는 `d1` 배치의 편차이고 **데모 배치 자체의 편차는 측정하지 않았다.**

## 3. 서버 교란 대상 재선정이 필요하다 — **중립**

`d1` 에서 `server` 교란은 S3 에만 걸었는데, 비교군은 S3 를 14~33% 만 쓰므로
end-to-end 로는 거의 보이지 않았다(site_s3 0.026→4.98% vs bl_rr 0.354→0.391%).
원인은 강도가 아니라 **대상 선정**이다: 교란된 S3(8.6 ms)가 여전히 S1(24~59 ms)보다
빨라 argmin 이 뒤집히지 않는다.

v9 에서 `server_s1`(S1 대상) 축을 새로 캘리브레이션했으나 **아직 본실험에 쓰지
않았다.** 이번 데모는 radio·ramp 만 포함한다.

## 4. 업스트림 DSB 버그 3종을 그대로 둔 것 — **중립**

① `CheckAvailability` 의 Mongo 폴백이 도달 불가 코드
② `cacheCap` 키 불일치 (호텔 1이 검색 결과에서 항상 제외 → 27→26개)
③ `rate` 가 캐시 미스마다 inventory 전량 조회

**두는 이유**: 세 사이트에 동일하게 작용하고(바이너리 md5 동일 확인),
고치면 부하 특성이 근본적으로 바뀌어 기존 캘리브레이션이 전부 무효가 된다.

**서술 시 주의**: "search 가 예약 가용성을 확인한다" / "예약이 쌓이면 search 가
느려진다"는 **쓸 수 없다.** 정확한 서술은 *search 는 geo → rate → reservation →
profile 의 4단 팬아웃을 만들며, 그중 reservation 단은 memcached 조회만 하고
영속 저장소에 접근하지 않는다.*

## 5. `f_c` 가 캐시 100% 적중 상태의 값 — **낙관**

`profile`·`rate` memcached 적중률이 **100.000%** 다(44시간 누적 미스 27건·5건).
파라미터가 완전 고정이라 항상 같은 키만 조회하기 때문이다.

| memcached | curr_items | 적중률 |
| --- | ---: | ---: |
| profile | 27 | 100.000% |
| rate | 5 | 100.000% |
| reserve | 2 | 3.962% |

**방향: 낙관.** `f_c` 절대값이 실서비스보다 작다.
다만 캐시가 공짜는 아니다 — search 1건이 여전히 rate 캐시에서 26,995 B 를 읽어
135개 plan 을 JSON 파싱하고 정렬한다.

**정책 비교에는 영향이 없다**(모든 정책·사이트가 같은 조건). **절대값 인용이
문제다.** "30.2 ms"를 "HR 의 응답시간"으로 쓰면 안 되고 "이 워크로드에서의 값"으로
한정해야 한다.

## 6. `GB` 5 ms 의 근거 부재 — **중립**

어떤 측정에서도 유도되지 않은 **설정(임의)** 값이다(provenance §4).
`GB` 는 slack 식에서 상수로 빠지므로 값이 바뀌면 계단 전이점이 통째로 이동한다.

관련 관측: T1 계단 실측 12칸 중 11칸이 기대와 일치했고, 유일한 불일치가
`S2`/극단(p50 44.06 ms = SLO 45 이내, 기대 "초과")이다. slack 표는 `f_c` p95+GB
기준이라 S2 를 불가로 보지만 p50 은 0.94 ms 여유로 살아남는다(p99 45.39 는 초과).
즉 **극단 밴드 전이의 이득은 p50 이 아니라 꼬리에서 난다.**

## 7. UERANSIM 에 물리계층이 없다 — **중립(모형 한계)**

UERANSIM v3.3.0 은 NAS/RRC/NGAP/GTP-U 를 구현한 **프로토콜 시뮬레이터**이고
물리계층·무선 채널 모델이 없다. 따라서:

- CQI/MCS·HARQ·스케줄러가 없다. 무선 열화는 ogstun 에 `netem rate` 로 **주입**한다.
- 컨트롤러가 읽는 "achievable rate"는 그래서 우리가 설정한 값 그 자체다(§1).
- 이동성·핸드오버·간섭·다중 사용자 스케줄링을 재현하지 않는다.

**방향: 중립이되 외부 타당성의 한계다.** 밴드 4개는 시나리오 정의값이지
측정된 무선 조건이 아니다(provenance §5).
