## 2. 용량 검사 로직 (A2)

소스: `~/DeathStarBench/hotelReservation` (배포 이미지는 세 사이트 모두
`deathstarbench/hotel-reservation:latest` 스톡, 로컬 수정 없음).

### 검사 방식과 단위

`services/reservation/server.go`:

* **검사 위치**: `MakeReservation` L179 `if count+int(req.RoomNumber) > hotel_cap { return res, nil }`
* **단위**: **호텔 × 숙박일(night)**. L115~183 이 밤 단위 루프이고 매 밤마다 검사한다.
  용량값 `hotel_cap` 은 호텔당(`number.numberOfRoom` = 1,000,000, L167·L171).
* **`count` 출처**: 1차 memcached 키 `<hotelId>_<night>_<night>` (L122),
  미스 시 Mongo `{hotelId, inDate, outDate}` 필터 (L135) — 인덱스가 없어 풀스캔.
  성공 후 `count+1` 을 같은 키에 되쓴다 (L186-188).
* **실패 응답**: `res.HotelId` 가 비어서 리턴 → `frontend/server.go:651`
  `str = "Failed. Already reserved. "` → 본문
  `{"message":"Failed. Already reserved. "}` + 개행 = **41 B**.
  (성공은 `{"message":"Reserve successfully!"}` = **36 B**, `EXPECT_BYTES` 와 일치.)

### 현재 남은 용량

최대치인 S1 기준 `1,000,000 − 41,521 = 958,479` (95.8% 여유).
런마다 drop+flush 되므로 **한 런이 만드는 최대 적재는 41,521건 = 용량의 4.2%**.

### 가설 "120만 건 요청 → 용량 초과": **거짓**

산술 자체는 맞다. reserve 요청 총량 = 런당 약 74,670건 × 16런 ≈ **119.5만 건**.
하지만 그것이 한 카운터에 쌓이지 않는다. 세 가지가 독립적으로 막는다.

1. **런마다 drop + flush** → 카운터가 매 런 0 에서 다시 시작. 최대 41.5k.
2. **사이트가 3개** → 각자 별도 Mongo·memcached. 합산되지 않는다.
3. **용량이 호텔×밤당 100만** → 전량 119.5만을 한 사이트에 몰아도 밤이 1개뿐이라
   겨우 초과하는 수준이고, 실제로는 1·2 때문에 근처도 못 간다.

**실측 확증**: 16런 4,608,000건 전수 스캔 결과
**HTTP 200 = 100%, 41 B 응답 0건**. reserve 는 항상 정확히 36 B.
즉 예약이 거절된 적이 **단 한 번도 없다**. 관측된 "실패 0건 + reserve p95 1.78 ms"
는 모순이 아니라 정상이다.

### search 가 reservation 을 읽는가: **호출은 하지만, Mongo 는 읽지 않는다**

* 호출은 한다: `frontend/server.go:267` `searchHandler` → `CheckAvailability`.
* 그러나 **Mongo 폴백이 도달 불가능한 죽은 코드**다.
  `CheckAvailability` 는 미스 판정을 `err == memcache.ErrCacheMiss` (L244, L343)
  로 하는데, `GetMulti` 는 키가 없어도 **`nil` 을 리턴한다**
  (`vendor/.../gomemcache/memcache/memcache.go:473-508` — 없는 키는 맵에 안 담고
  에러도 안 낸다). 따라서 L343 블록이 절대 실행되지 않는다.
* 결과: **search 는 `reservation` 컬렉션을 한 번도 읽지 않는다.**
  → "예약 누적이 검색을 느리게 한다"는 드리프트 경로는 **존재하지 않는다.**

### 부수 발견 — 왜 search 가 항상 26개인가 (27개가 아니라)

같은 죽은 코드가 두 가지 부작용을 낳는다.

* 캐시에 카운트가 **없는** 호텔은 `resMap` 초기값 `true` (L231) 그대로 →
  **가용성 검사가 사실상 수행되지 않는다.**
* 캐시에 카운트가 **있는** 호텔은 반드시 거절된다: `cacheCap` 을 채울 때는
  키가 `"1_cap"` (L257) 인데 읽을 때는 `"1"` (L329) 이라 항상 0 →
  `val+1 <= 0` 이 거짓.

reserve 트래픽이 채우는 유일한 키가 호텔 `"1"` 이므로 **호텔 1만 검색 결과에서
빠진다** → 27 → 26. 워밍업 60초 안에 전이가 끝나므로 측정구간은 전부 26개
(=4474 B) 로 일정하다. `EXPECT_BYTES` 검증이 깨끗한 이유이자, 동시에
"26개"가 물리적 의미가 아니라 **버그의 산물**이라는 뜻이다.

실험 중 적중률이 변했을 가능성은 배제된다. 배경의 evictions 우려는 **해소**.

reserve 3.96% 의 정체: `curr_items = 2` 뿐이다(`1_2015-04-10_2015-04-10`, `1_cap`).
search 1건이 `GetMulti` 로 호텔 27개의 cap 키 + 27개 날짜 키 = 54회 조회하는데
채워진 키가 2개뿐이라 구조적으로 영구 미스다(§2 의 죽은 코드). 캐시 문제가 아니라
**미스가 Mongo 로 내려가지도 않는** 상태다.

**`rate` 의 80,385 B(S1/S2) vs 53,690 B(S3)** — 이 1.497× 격차가 §1 의 시드 배수
불일치가 성능에 드러나는 지점이다. §6-7 참조.

## 6. 타당성 (A6)

### 6.1 파라미터 고정 → 캐시 100% 적중

* **(a) 현재**: profile·rate 적중률 100.000%, 미스 총 27·5건. curr_items 27·5.
* **(b) 영향**: `f_c` 절대값이 실서비스보다 낙관적이다. 다만 DB 접근이 아예
  사라진 것은 아니다 — search 는 매 요청 rate 캐시에서 53.7~80.4 KB 를 읽어
  270~405개 plan 을 JSON 파싱하고 정렬한다(§6.7). 즉 "캐시=공짜"가 아니라
  "캐시=고정 비용"이다.
* **(c) 방어**: 정책 비교는 유효하다(모든 정책·사이트가 동일 조건).
  **절대값 인용은 방어 불가.** 논문에서 30.2 ms 같은 값을 "HR 의 응답시간"으로
  쓰면 안 되고 "이 워크로드에서의 값"으로 한정해야 한다.
* **(d) 개선·비용**: 생성기에 `hotelId`/`lat`/`lon`/날짜 무작위화 추가.
  코드 수정 소(小), **재측정 16런 ≈ 2시간 20분**. 단 무작위화하면 rate 캐시
  미스가 생겨 `Find(bson.D{})` 전체 스캔이 매번 터지므로(§6.7) 부하 특성이
  크게 바뀐다 — **캘리브레이션부터 다시** 해야 한다.

### 6.2 reserve 가 호텔 1개에 집중

* **(a)** 표 A1 대로 100%가 `hotelId=1`, 단일 날짜.
* **(b)** 락 경합·핫스팟 우려는 **실측상 발생하지 않았다**: reserve `f_c` p95 가
  S3 1.78 ms, S2 2.5~3.2 ms 로 전 런 안정적이고 41 B 거절 0건.
  Mongo 쪽 경합이 없는 이유는 쓰기가 인덱스 없는 `InsertOne` 1건뿐이고
  읽기는 캐시에서 끝나기 때문이다. 실제 경합은 memcached 카운터의
  read-modify-write 에 있고, 그건 lost update 로 흡수된다(§4.2, 75건 차이).
* **(c)** 방어 가능. "단일 핫 키가 병목이 아님"을 위 수치로 보이면 된다.
* **(d)** §6.1 과 같은 수정에 포함. 추가 비용 없음.

### 6.3 search 가 항상 같은 26개 반환

* **(a)** 세 사이트 모두 26개 distinct, 4474 B. 4,608,000건 전수에서 바이트 이탈 0건.
  단 순서는 요청마다 다르다(Go 맵 순회) — 크기는 같다.
* **(b)** **이점**: `d_acc` 계산이 정확해진다(4474 B = 35,792 bit 고정).
  램프 분석의 "4.9→3.3 Mbit/s 에서 깨진다"가 이 고정 크기 덕에 성립한다.
  **손실**: 다양성 없음. 그리고 26이라는 수 자체가 §2 의 `cacheCap` 키 버그
  산물이라 물리적 의미가 없다.
* **(c)** 방어 가능하되 **26의 의미를 주장하면 안 된다.** "응답 크기를 4474 B로
  고정했다"까지만 쓰고, 호텔 수는 언급하지 않는 편이 안전하다.
* **(d)** 개선 불필요. 오히려 고정이 이 실험 설계의 강점이다.

### 6.4 DB 가 실험 내내 단조 증가 → **전제가 거짓**

* **(a)** 단조 증가하지 않는다. 런마다 drop+flush 되어 매 런 0에서 시작한다(§1, §3).
* **(b)** 순서 효과 없음 — §6.8 에서 정량화.
* **(c)** 방어 가능. `reserve_reset.sh` 와 `cmd_flush` 카운터를 증거로 제시.
* **(d)** 조치 불필요. 단 R3(리셋 결과 로깅)은 해 두는 게 좋다.

### 6.5 `bl_loc` 전 조건 100% 위반

* **(a)** 16런 중 4런 모두 pre/during/post 전부 100.000%.
  달성 636/s (목표 800/s), corrected p50 ≈ 24초. `s1_knee_ratio` 1.143
  (S1 유입 457 rps vs 무릎 400, 안정용량 200).
* **(b)** 정보량이 거의 0인 것은 맞다. 더 심각한 것은 **세 엔드포인트의 p50 이
  서로 같다**는 점이다 (24,656 / 24,732 / 24,701 ms). 이는 엔드포인트별 서비스
  품질이 아니라 **공유 keep-alive 커넥션의 head-of-line 지연**을 재고 있다는 뜻이다.
  즉 이 값은 "생성기 백로그"지 "응답시간"이 아니다.
* **(c)** "평상시부터 깨진다"의 증거로는 **방어 가능**. 단
  **엔드포인트별 수치는 인용하면 안 된다**(전부 같은 백로그 값이다).
  100% 를 다른 정책의 0.2~1.5% 와 같은 축에 놓는 것도 오해를 부른다.
* **(d)** 두 안. ① 현행 유지 + "포화 증거"로만 사용 — 비용 0.
  ② `bl_loc` 만 λ 를 낮춰(예: 400 rps, S1 유입 229 ≈ 안정용량 근처) 별도 측정 —
  **4런 ≈ 35분**. 정책 비교표에는 못 넣고 별도 절이 된다.
  **권고: ①. 다만 표에서 분리 표기하고 각주로 백로그임을 명시.**

### 6.6 서버 교란이 작동하지 않음

* **(a)** 교란은 **걸렸다**. S3 `f_c` p95 pre→during:
  site_s3 6.41→21.12 (3.30×), bl_rr 4.84→8.57 (1.77×), bl_lr 4.80→8.14 (1.69×),
  bl_loc 4.79→7.31 (1.53×). 다만 end-to-end 위반율은
  site_s3 0.026%→4.98% 인데 비교군은 bl_rr 0.354%→0.391%, bl_lr 1.269%→1.435% 로
  **사실상 무반응**이다.
* **(b)** 두 겹의 희석이다. ① S3 몫이 14~33%뿐이다. ② 교란된 S3(8.6 ms)가
  **여전히 S1(24~59 ms)보다 빠르다** → least-request 의 argmin 이 안 뒤집힌다.
  ②가 본질이고, 이는 §1 의 시드 배수 불일치(S3 가 구조적으로 가장 가벼움)와
  하드웨어 차이가 함께 만든 것이다.
* **(c)** "교란이 안 걸렸다"가 아니라 **"교란해도 S3 가 최속이라 정책이 반응할
  이유가 없다"** 로 쓰면 방어 가능하다. `f_c` 표(3b)가 그 근거다.
  현재 분석노트 §4.2 가 이미 이렇게 쓰고 있고, **그 서술이 옳다.**
* **(d)** 교란 대상을 **S1 또는 S2 로 옮기는 것**이 맞다. 특히 S1 은 이미
  최속이 아니므로 교란하면 argmin 이 실제로 움직인다. 다만 S1 은 이미
  안정용량을 넘긴 상태라 교란 강도 재캘리브레이션 필요.
  **비용: 캘리브레이션 + 4~8런 ≈ 1~1.5시간.**
  대안으로 S3 교란 강도를 올려 S3 를 최속에서 끌어내리는 방법
  (`--cpu 3` 이상)도 있으나, `tb-stress.sh` 주석대로 800 rps 에서는 과도해진다.

### 6.7 `rate` 캐시에 구워진 대용량 페이로드 — **"세 사이트 동일"이 거짓**

이것이 §1 발견의 귀결이며, 배경 표의 7번 항목을 **정정**해야 한다.

* **(a)** `rate/server.go:141` 이 캐시 미스 시 특정 호텔이 아니라
  **컬렉션 전체**를 읽는다: `collection.Find(context.TODO(), bson.D{})`.
  그 전량을 호텔 키 하나에 구워 넣는다(L169-171). geo 가 5개를 주므로
  search 1건당 5개 키를 읽고, 각 키가 inventory 전량이다.

  | | inventory 문서 | 키당 크기 | search 1건당 | plan 수 |
  | --- | ---: | ---: | ---: | ---: |
  | S1 / S2 (3× 시드) | 81 | 16,077 B | **80,385 B** | **405** |
  | S3 (2× 시드) | 54 | 10,738 B | **53,690 B** | **270** |

* **(b)** **세 사이트가 동일하지 않다. S1/S2 는 search 1건당 S3 의 1.497배를
  읽고 파싱하고 정렬한다**(`sort.Sort` 는 O(n log n)). 배경이 인용한 53.7 KB /
  280 plan 은 **S3 값**이며, S1/S2 는 80.4 KB / 405 plan 이다.
  이는 사이트 간 `f_c` 격차(S1 8.6~22 vs S3 4.0 ms)의 **일부가 하드웨어가 아니라
  시드 아티팩트**임을 뜻한다. 그리고 정책은 정확히 "사이트 분배"로 구분되므로,
  **S1/S2 로 더 보내는 정책이 구조적으로 불리해진다** — 정책 효과와 시드
  아티팩트가 교락돼 있다.
* **(c)** "업스트림 그대로"는 `Find(bson.D{})` 버그에 대해서만 방어 가능하다.
  **시드 배수 불일치는 업스트림이 아니라 우리 환경 구축 실수이므로 방어 불가.**
  현재 결과로 사이트 간 `f_c` 를 비교하거나, 정책 간 차이를 "사이트 용량 차이"로
  귀속시키는 서술은 **쓸 수 없다.**
* **(d)** 세 사이트의 시드를 동일 배수로 맞춘다. 컨테이너 재시작 없이
  중복 문서만 제거하면 되므로(각 컬렉션에서 `hotelId` 중복 삭제) 값싸다.
  **단 이후 전 구간 재측정 필요: 캘리브레이션(무릎 재측정) + 16런 ≈ 3~4시간.**
  대안(비용 0): 사이트 간 비교를 일절 하지 않고 **정책 간 비교만** 보고하되,
  교락을 명시적으로 한계로 기술. 다만 §6.6 의 "S3 가 최속이라 argmin 이 안
  움직인다"가 핵심 결론이므로 이 교락은 결론의 중심에 있다 — **권고: 수정 후 재측정.**

### 6.8 순서 효과 정량 (§7.1)

매니페스트가 `none`(1-4) → `radio`(5-8) → `server`(9-12) → `ramp`(13-16) 순서라
교란 종류와 실행 순서가 완전히 겹친다. 두 `pre` 구간은 모두 교란 전이므로
차이가 있으면 순서 효과다.

| 정책 | reserve p50 | search p50 | search p95 | recommend p50 |
| --- | ---: | ---: | ---: | ---: |
| site_s3 | −0.04% | −0.19% | +0.06% | −0.24% |
| bl_rr | −2.48% | −1.88% | −0.76% | +1.74% |
| bl_lr | −0.38% | −0.24% | −1.01% | −0.03% |
| bl_loc | −4.51% | −4.55% | −2.50% | −4.59% |

**최대 |4.6%|, 12개 중 10개가 음수** (뒤 런이 오히려 빠르다).
누적성 열화라면 전부 양수여야 하므로 **순서 효과는 검출되지 않았다.**

교란 효과와의 비교 (site_s3, S3 `f_c` p95): 순서 효과 0.06% vs 교란 효과 **+230%**.
end-to-end 위반율로는 0.026% → 4.98%.

**판정: 순서 효과 ≪ 교란 효과. `server` 런은 사용 가능하다.**
(`server` 가 비교군에서 안 보이는 이유는 순서가 아니라 §6.6 이다.)

## 7. 종합 판정

### 그대로 쓸 수 있는 범위

1. **정책 간 비교 전체** — 드리프트·순서 효과 모두 검출 한계 이하.
2. **`site_s3` 의 교란 응답**(radio 25.3%, server 4.98%, ramp 21.0%) — 단일 사이트라
   시드 교락이 없다.
3. **램프 분석과 `T_dep`**(4.9→3.3 Mbit/s) — 4474 B 고정 덕에 물리적으로 검산된다.
4. **데이터 무결성** — 조인율 16/16런 1.000, 200 응답 100%, 바이트 이탈 0건,
   시계 오차 ±17 ms(가드 2초). 이 축은 매우 튼튼하다.
5. **`bl_loc` 를 "평상시부터 포화"의 증거로 쓰는 것** (엔드포인트별 수치는 제외).

### 재측정이 필요한 범위

1. **사이트 간 `f_c` 비교 및 그에 근거한 서술** — 시드 배수 교락(§6.7).
   시드 정규화 후 캘리브레이션 + 16런 = **3~4시간**.
2. **`B_ramp_bl_rr`** — S1 상태 이탈(§3.4). 단독 재실행 **약 9분**,
   다만 반복 없이는 재발 여부를 알 수 없으므로 **3반복 ≈ 25분** 권장.
3. **서버 교란 축 전체** — 대상 재선정(S1/S2) 필요(§6.6). 캘리브레이션 + 4~8런
   = **1~1.5시간**. 1번 재측정과 합치면 추가 비용 작다.

### 다음 실험 전에 반드시 고쳐야 할 것 (우선순위)

1. **세 사이트 시드 배수 통일** — 유일하게 결론을 무효화할 수 있는 문제.
2. **런당 반복 ≥3** — 현재 셀당 n=1 이라 `B_ramp_bl_rr` 같은 이탈을 잡을 방법이 없다.
3. **교란 대상 재선정** (S3 → S1/S2).
4. **실행 순서 무작위화 / 라틴방격** — 이번엔 순서 효과가 0이었지만 그건 운이 아니라
   확인된 사실일 뿐이고, 설계로 보장된 것은 아니다.
5. **리셋 결과 로깅**(R3) 및 런별 사이트 상태 스냅샷(R4).
