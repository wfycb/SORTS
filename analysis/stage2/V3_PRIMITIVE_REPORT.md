## 1. §3-1 — `read_rates()` 집계 규칙 (가설 적중)

정규식 `qdisc netem …: parent 1:(…) .*?rate (\d+)([KMG]?)bit` 는 **`rate`
속성이 있는 leaf 만** 잡는다. 더미 인터페이스 실측:

```
qdisc netem 1002: parent 1:1002 limit 1000 rate 2300Kbit   -> 파싱됨
qdisc netem 1001: parent 1:1001 limit 1000                 -> 파싱 안 됨(무제한)
파싱 모집단 {0x1000: {2300.0: 1}}  ->  read_rates = {0x1000: 2300.0}
```

- **집계 모집단은 "64 leaf"가 아니라 "값이 잡힌 leaf"** 이고 그 안에서 최빈값.
  v2 에서 leaf 14개만 있어도 전부 2300 이므로 최빈값 = 2300 — §4-3 의
  모순은 이것으로 해소된다(모순 아님).
- **따라서 지시하신 "선구축" 방식은 표현에 따라 갈린다**: 무제한 leaf 를
  `netem`(rate 없음)으로 두면 파싱에서 탈락해 뒤집힘이 **1/64**에서 오고,
  `netem rate 10000mbit` 로 두면 **33/64**에서 온다. 전자는 v2 와 같은 문제가
  남고, 후자는 사전 무해하지만 **런 내내 ogstun 에 HTB 트리가 상주**해
  베이스라인 데이터패스가 바뀐다(전 결과와의 연속성 위험).

## 2. §2 채택안의 구현 — 지시안(선구축)에서 벗어난 점과 이유

**구현한 것**: (A) 전 명령을 `tc -batch` **단일 호출**로, (B) 코호트마다
**classes → filters → netem(rate)** 순서로 재배열.

- (B)가 목표를 직접 달성한다: 필터가 먼저 붙으므로 **어떤 leaf 의 rate 가
  보이는 순간 그 버킷은 이미 셰이핑된다** = 가시화 ≡ 발효. 선구축이 필요 없다.
- (A)로 전체가 원자에 가깝게 끝난다 — 더미 인터페이스 실측 196 명령 **10 ms**
  (v2 는 프로세스 194회 스폰 0.86 s).
- **선구축을 쓰지 않은 이유 3가지**: ① 베이스라인 데이터패스 불변(주입 전
  ogstun 은 종전대로 fq_codel — §4-1 등가성이 구조적으로 성립), ② 선구축
  호출 지점이 러너에 없어 `run_all.py`(**FREEZE 6파일**) 수정이 필요해짐 —
  현 해제 범위(주기 파라미터화) 밖이라 금지, ③ 뒤집힘 시점이 1/64 냐 33/64 냐
  하는 문제 자체가 사라진다(전 leaf 가 같은 배치에서 붙음).
- 최종 상태(클래스·필터·해시키·rate 의미)는 **v2 와 동일**하다. 롤백은
  `/usr/local/sbin/tb-radio2.sh.v2.bak`(md5 `58c9e391…` = 저장소 사본과 일치).

### 3.1 트래픽 발효 교차검증 — 시계 편향을 상쇄한 비교

부하 기록은 `.12` 시계라 `.43` 변환에 러너 자체 주석이 경고한 "수십 ms
편향"이 있다(ssh RTT 비대칭). 편향을 **두 런의 차이로 상쇄**했다:

| 항목 | v2 | v3 | 차이 |
|---|---|---|---|
| 측정 발효(송신 기준, `.12`→`.43` 변환) | +0.603 s | +0.341 s | **0.262 s** |
| 기전 예측 발효( = F1, 폴러 `.43` 현지) | +0.52 s | +0.256 s | **0.264 s** |

차이가 **2 ms 이내 일치** → 변환 편향은 두 런에서 동일한 상수(+0.083/+0.085 s)
이고, 편향 제거 후 **두 런 모두 "트래픽 발효 = 필터 부착 시점"** 이다.
v2 의 0.52(필터) vs v3 의 0.256(필터=leaf) 이 각각 재현된다.
개별 요청 수준으로도 경계가 날카롭다(v3: 송신 +0.336 비셰이핑 → +0.346
셰이핑, 10 ms 간격).

> 부기: `.43` 현지 시계인 **Envoy 액세스 로그로는 이 검증이 불가능**하다 —
> 필드16(DS_RX_BEG:DS_TX_END)이 셰이핑 전후로 19~20 ms 그대로다. 이는 오류가
> 아니라 논문 §1 의 "Envoy 구조적 무관측"(1024:1) 이 그대로 나타난 것이다:
> Envoy 는 커널에 넘긴 시점까지만 보므로 ogstun netem 의 15.6 ms 를 못 본다.
> 검증에 쓸 수 없다는 사실 자체가 주장의 재확인이다.

## 4. §4 등가성 검증

### 4-1 정상 상태 등가 (주입 전)

v3 는 선구축을 하지 않으므로 주입 전 ogstun 은 **종전과 동일한 fq_codel**
(구조적 등가). 실측(각 런 pre 창 n=7,800, c1):

| 클래스 | v2 pre p50/p95 | v3 pre p50/p95 |
|---|---|---|
| search | 20.7 / 28.9 ms | 21.5 / 29.1 ms |
| reserve | 17.4 / 26.5 ms | 16.7 / 26.3 ms |
| recommend | 17.2 / 26.1 ms | 17.4 / 26.2 ms |

차이 ≤ 0.8 ms — 런간 변동 범위. 도착률 800.0/799.9 rps, 조인율 1.0,
바이트 이탈 0 (양 런).

### 4-2 발효 결과 등가 (주입 후 정상 상태, n=7,600)

| 클래스 | v2 post p50/p95 | v3 post p50/p95 |
|---|---|---|

### 4-3 램프 소멸과 새 반응 시각 분해

| 구간 | v2 | v3 |
|---|---|---|
| 지시 → tc 적용 시작(=가시화=발효) | 0.26 s | **0.256 s** |
