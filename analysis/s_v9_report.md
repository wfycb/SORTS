대해 `_id` 를 제외한 전 필드를 문자열 비교했다.

* 배수가 군마다 균일: S1/S2 전부 `{3: n}`, S3 전부 `{2: n}`

즉 중복은 완전한 사본이고, 어느 1건을 남겨도 동일하다.

## 3. M1 재측정 (S3)

### 표 S3-1. `f_c` (무부하 service p95, ms) 이전 → 이후

| | reserve | search | recommend |
| --- | --- | --- | --- |
| S1 | 1.658 → 2.378 (+43.4%) | 8.624 → **6.899 (−20.0%)** | 1.240 → 1.233 (−0.6%) |
| S2 | 1.332 → 1.337 (+0.4%) | 6.475 → **4.287 (−33.8%)** | 0.975 → 0.977 (+0.2%) |
| S3 | 1.348 → 1.251 (−7.2%) | 5.070 → **4.019 (−20.7%)** | 1.000 → 0.906 (−9.4%) |

**S1 reserve 의 +43.4% 는 실제 열화가 아니라 꼬리 잡음이다.** 분포 전체:

```
S1/reserve  이전 p50=1.325 p90=1.467 p95=1.658 p99=2.917 max=34.141
            이후 p50=1.318 p90=1.464 p95=2.378 p99=3.428 max=41.693
```

p50·p90 이 소수 셋째 자리까지 같고 p95 부터 벌어진다. 1200 표본에서 p95 는
1140번째 값이라 1코어 cpuset 의 스트래글러 몇 건에 흔들린다.
반면 search 는 p50 이 6.606→4.358 로 **분포 전체가 이동**했다 — 이쪽이 진짜 효과다.

### 남은 비대칭에 대한 보고 (지시서 §4.2 가 요구한 것)

지시서는 "정규화 후 세 값이 비슷해지는 것이 자연스럽다"고 했다.
**S2 는 수렴했고(1.277→1.067) S1 은 수렴하지 않았다(1.701→1.716).** 원인:

* 세 사이트는 **동일 하드웨어**다 — Intel i5-8500T, nproc=6, load 0.00,
  컨테이너 24개, 전부 idle 상태에서 측정.
* 차이는 cpuset 뿐이다. `docker-compose.yml` 에 사이트별로 명시돼 있다:
  **S1 `0` (1코어) / S2 `0-1` (2코어) / S3 `0-3` (4코어)**.
* 20 rps 무부하라도 DSB 요청 1건은 frontend→search→geo→rate→reservation→profile
  6개 프로세스를 거친다. 1코어에 24컨테이너가 묶이면 체인이 **컨텍스트 스위치로
  직렬화**되므로, 데이터 볼륨을 줄여도 S1 은 개선되지 않는다.

즉 "`f_c` 는 무부하 지연이라 코어 수에 비례하지 않는다"는 전제가 이 마이크로서비스
체인에는 성립하지 않는다. **남은 비대칭은 시드 아티팩트가 아니라 의도된 3계층
이질성**(edge 1 / regional 2 / central 4 코어)이므로 제거 대상이 아니다.
S6 의 결론 1(§6)도 같은 메커니즘이다.

## 5. 파라미터 재계산 (S5) — 계산만, 확정 안 함

### 도착률 후보

```
기준 = S3 단독 마지막 안정 용량 = 1600 rps
후보 = 1600 x 0.67 = 1072 rps     (이전: 1200 x 0.67 = 804 -> 800 채택)
```

**그러나 이 값을 그대로 쓰면 비교군이 깨진다.** 도착률은 S3 단독 용량에서
유도되는데, 비교군 정책은 부하를 S1(무릎 400)에도 뿌리기 때문이다.

| 도착률 | site_s3 | bl_rr | bl_lr | bl_loc |
| --- | ---: | ---: | ---: | ---: |
| 800 (구) | 0 | 267 (0.67) | 319 (**0.80**) | 457 (**1.14 포화**) |
| **1072 (신 후보)** | 0 | 357 (0.89) | 428 (**1.07 포화**) | 613 (**1.53 포화**) |
| 600 (참고) | 0 | 200 (0.50) | 239 (0.60) | 343 (0.86) |

괄호는 S1 무릎(400) 대비 비. **1072 에서는 4개 정책 중 2개가 교란 전부터
포화**다. 800 에서는 1개(bl_loc)만 포화였다. 즉 정규화로 용량이 늘었는데도
도착률을 같은 비율로 올리면 비교군 상황은 **나빠진다**.

### 계단 존속 판정

지시서 §6.3 의 세 범주를 그대로 적용하면 **search 는 어디에도 정확히 맞지 않는다.**

| 지시서 정의 | 우리 결과 |
| --- | --- |
| 유지 = Poor 에서 S2 로, **극단에서 S1 으로** 이동 | Poor→S2 **O**, 극단→S1 **X** (S2 에 머묾) |
| 약화 = 극단에서만 이동 | X (Poor 에서 이미 이동) |
| 소멸 = 전 밴드 S3 | X |

**판정: search = 부분 유지.** 핵심 전이(Poor 에서 S3 이탈)는 살아 있으나
극단 계층(S2→S1)이 사라져 계단이 3단에서 2단으로 얕아졌다.
**reserve·recommend = 계단 소멸** (현행 SLO 35 ms 에서는 전 밴드 S3).

정규화 전후 비교 (같은 SLO, 구 `f_c` vs 신 `f_c`):

| | 정규화 전 | 정규화 후 |
| --- | --- | --- |
| reserve | S3 → S3 → S3 → S3 | S3 → S3 → S3 → S3 (변화 없음) |
| **search** | S3 → S3 → S2 → **S1** | S3 → S3 → S2 → **S2** (★얕아짐) |
| recommend | S3 → S3 → S3 → S3 | S3 → S3 → S3 → S3 (변화 없음) |

얕아진 이유: 극단 밴드에서 S2 의 slack 이 −1.03 → **+1.16** 으로 부호가 바뀌었다
(S2 search `f_c` 6.475→4.287). S2 가 가능해지면 "최원거리" 규칙상 S1 이 아니라
S2 가 선택된다. **정규화가 계단을 만든 게 아니라 한 칸 지웠다.**

### 계단이 성립하는 SLO 구간 (Poor 밴드 기준)

```
SLO < GB + d_net(S3) + f_c(S3) + d_acc(Poor)    (S3 불가)
SLO > GB + d_net(S2) + f_c(S2) + d_acc(Poor)    (S2 가능)
```

| 클래스 | 구간 (ms) | 중앙값 | 현 SLO | 현 SLO 가 구간 안? |
| --- | --- | ---: | ---: | --- |
| reserve | (17.37, 32.29) | 24.83 | 35.0 | **밖** |
| search | (36.36, 51.10) | 43.73 | 45.0 | **안** |
| recommend | (17.55, 32.49) | 25.02 | 35.0 | **밖** |

**세 클래스 동시 성립: 가능.** SLO 는 클래스별 독립 파라미터이므로 각 구간에서
하나씩 고르면 된다. 예: reserve 25 / search 45 / recommend 25.
현행값에서 바꿔야 하는 것은 **reserve 35→약 25, recommend 35→약 25** 두 개다
(search 45 는 이미 구간 안이라 그대로 두면 된다).

### 결론 1 — `--cpu-load` 에 레버리지가 없다

응답이 강도에 대해 **평평한 계단**이다.

* S1 @800: load 10 → 3.20× / 20 → 3.14× / 30 → 3.11× (강도를 3배 올려도 오히려 감소)
* S3 @1072: load 10 → 5.45× / 50 → 5.41× / 100 → 5.12×
* S3 @800: `cpu2/load80`(2.50×) 이 `cpu1/load100`(2.92×) 보다 **낮다**

원인은 §3 의 cpuset 논의와 같다. DSB 요청 1건이 6개 이상 프로세스 체인을 거치므로,
같은 cpuset 에 CPU-bound 프로세스가 **존재하는 것 자체**가 스케줄링 지연을 고정량
얹는다. 뺏는 CPU 총량은 부차적이다. 지시서 §7.3 의 "`--cpu-load` 를 10 단위로
올리며 최소 강도를 찾는다" 는 절차는 **이 시스템에서 작동하지 않는다** —
최소 강도랄 것이 없고, 켜면 곧바로 최대 효과가 난다.

### 결론 2 — 상승배수를 정하는 것은 강도가 아니라 도착률이다

같은 `cpu2/load80` 이 800 rps 에서 **2.50×**, 1072 rps 에서 **5.08×** 다.
**도착률 1072 에서는 어떤 강도로도 2~4배 창에 들어갈 수 없다.**
(구 캘리브레이션이 `cpu1/load100` 에서 1.74× 를 봤던 것도 같은 이유다 —
그때는 800 rps 였고 seed 가 3×/2× 여서 여유가 달랐다.)

### 확정 강도 (도착률 800 rps 에서만 유효)

해당하지 않는다 — 오히려 최저 강도에서도 3배가 넘는다.
강도가 평평하므로 load 10/20/30 중 무엇을 써도 같다. 여유를 위해 30 을 택했다.

비 0.80 이다. `server_s1` 이 유의미한 축이 될 수 있는 전제가 이번에 갖춰졌다.

## 7. 업스트림 버그 3종 정리 (논문용)

세 버그 모두 **세 사이트에 동일한 이미지**(`deathstarbench/hotel-reservation:latest`,
세 사이트 digest 동일 확인)에서 동일하게 작동한다. 손대지 않았다.

### (1) `CheckAvailability` 의 도달 불가능한 Mongo 폴백

* **위치**: `services/reservation/server.go:244`, `:343`
* **동작**: 미스 판정을 `err == memcache.ErrCacheMiss` 로 하는데,
  `GetMulti` 는 키가 없어도 `nil` 을 리턴한다
  (`vendor/github.com/bradfitz/gomemcache/memcache/memcache.go:473-508` —
  없는 키는 맵에 담지 않고 에러도 만들지 않는다). 따라서 두 분기 모두 죽은 코드다.
* **실험에 미친 영향**: **search 는 `reservation` 컬렉션을 한 번도 읽지 않는다.**
  캐시에 카운트가 없는 호텔은 `resMap` 초기값 `true`(L231) 그대로라
  **가용성 검사가 실질적으로 수행되지 않는다.**
* **동일성 근거**: 코드 경로이므로 사이트 무관. 표 S3-4 의 reserve 적중률이
  세 사이트 3.704% 로 자릿수까지 같은 것이 실측 증거다.

### (2) `cacheCap` 키 불일치

* **위치**: `services/reservation/server.go:257` (쓰기) vs `:329` (읽기)
* **동작**: `cacheCap[k]` 의 `k` 는 `"1_cap"` 인데 읽을 때는 `cacheCap[id]` 의
  `id` 가 `"1"` 이다. 항상 0 이 나와 `val+1 <= 0` 이 거짓 → **캐시에 카운트가
  있는 호텔은 반드시 거절된다.**
* **실험에 미친 영향**: reserve 트래픽이 채우는 유일한 키가 호텔 `1` 이므로
  **호텔 1 만 검색 결과에서 빠진다** → 27 → 26개, 4632 → 4474 B.
  즉 "search 가 26개 호텔을 돌려준다"는 것은 물리적 의미가 아니라 버그의 산물이다.
  워밍업 60초 안에 전이가 끝나 측정구간은 항상 4474 B 로 안정적이다.
* **동일성 근거**: §2 에서 세 사이트 모두 26개 / 4474 B 실측.

### (3) `rate` 의 전체 스캔

* **위치**: `services/rate/server.go:141` — `collection.Find(context.TODO(), bson.D{})`
* **동작**: 특정 호텔의 캐시 미스인데 **inventory 컬렉션 전량**을 읽어 그 전량을
  그 호텔 키 하나에 구워 넣는다. geo 가 5개를 주므로 search 1건당 5키 × 전량이다.
* **실험에 미친 영향**: search 1건당 파싱량이 **5 × 27 = 135 plan / 26,995 B**.
  이 버그가 v9 이전에는 시드 배수 불일치를 **1.497배로 증폭**시켜 사이트 간
  교락을 만들었다(S1/S2 405 plan vs S3 270 plan). 시드 정규화로 세 사이트가
  135 plan 으로 통일됐다.
* **동일성 근거**: `rate` memcached `bytes` 가 세 사이트 26,995 B 로 동일(§1).

### "search 는 예약 DB 를 읽지 않는다" 가 워크로드 서술에 주는 영향

논문의 워크로드 절에서 다음 두 문장은 **쓸 수 없다.**

1. "search 는 예약 가용성을 확인한다" — gRPC 호출은 하지만 실질 검사가 없다.
2. "예약이 쌓이면 search 가 느려진다" — 읽는 경로가 없어 성립하지 않는다.

대신 정확한 서술은: *search 는 geo → rate → reservation(가용성) → profile 의
4단 팬아웃을 만들며, 그중 reservation 단은 memcached 조회만 수행하고 영속
저장소에 접근하지 않는다.* 이렇게 쓰면 사실이고, 팬아웃 구조라는 실험의
핵심 성질도 유지된다.

덧붙여 **`d1-20260804` 결과에는 이 버그들이 오염을 만들지 않았다.** v8 감사가
확인한 대로 4,608,000건 전수에서 200 응답 100%, 바이트 이탈 0건, 41 B(예약 거절)
0건이다.
