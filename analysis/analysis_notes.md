## 4. 지시서의 기대와 어긋난 것 (전부 관측대로 보고)

### 4.1 `bl_lr` 의 `s1_knee_ratio` 가 0.80 (기대 0.56)
16런 전부에서 `bl_lr` 의 S1 몫이 0.40 (기대 0.28) 이다. pre/during 모두 같고
교란 종류와 무관하다. 조인율 1.0, 바이트 이탈 0 이므로 데이터 문제는 아니고
정책 거동이 v5 계획 시점의 예상과 다르다는 뜻이다.

참고로 S1 **안정 용량은 200 rps, 무릎은 400 rps** 다. 800 rps 기준 S1 유입은
site_s3 0 / bl_rr 267 / bl_lr 320 / bl_loc 457 rps 로, **site_s3 를 뺀 세 정책은
모두 S1 안정 용량을 넘긴 상태**에서 측정됐다.

### 4.2 서버 교란에서 `bl_lr` 이 반응하지 않았다 (지시서 §5 의 전제와 반대)
네 정책 모두 분배 반응 없음. 원인을 `f_c` 로 확인했다 (표3b):

| 정책 | S3 몫 | S3 `f_c` p95 pre→during | 같은 런 S1 `f_c` p95 |
| --- | ---: | --- | ---: |
| site_s3 | 100% | 5.50 → **16.66** ms (3.03×) | — |
| bl_rr | 33% | 4.43 → 6.62 ms (1.49×) | 17.4 |
| bl_lr | 23% | 4.43 → 6.35 ms (1.43×) | 36.2 |
| bl_loc | 14% | 4.39 → 5.71 ms (1.30×) | 276 |

교란은 걸렸다. 다만 비교군 런에서는 S3 가 부하의 14~33% 만 받으므로 열화가
+1.3~2.2 ms 에 그치고, **그 크기가 사이트 간 상시 격차보다 훨씬 작다**
(bl_lr 기준 S1 36 ms vs 열화된 S3 6.35 ms). 즉 stress 를 걸어도 S3 가 여전히
가장 빠른 사이트라 least-request 의 argmin 이 뒤집히지 않는다.
`site_s3` 의 "무반응"은 선택지가 하나뿐이라 구조상 당연하다.

판정 규칙은 명시적으로 고정했다: pre 1초 bin 의 S3 몫 평균 mu·표준편차 sd,
임계 `mu - max(3sd, 2.0%p)`, **연속 3 bin** 유지. 규칙을 느슨하게 해도
`bl_lr` 의 최대 순간 이탈이 2.02 %p (3sd = 2.36 %p) 라 유의하지 않다.

### 4.3 램프의 T1/T5 가 램프 효과가 아니다
**네 런 모두 T1 이 step 0 (=20 Mbit/s, 아직 안 떨어진 시점)** 에 걸린다.
`bl_rr` 7.58% / `bl_lr` 3.90% / `bl_loc` 100% 는 **램프 시작 전부터** 1% 를
넘고 있어서, 절대 임계 1%/5% 로는 램프 귀속이 불가능하다. `site_s3` 의
T1(+8.94s)도 1초짜리 단발 blip(3%)이고 그때 전송률은 아직 20 Mbit 이다.

그래서 보조 지표 **`T_dep`**(기준선 이탈: 3초 이동평균이
`base_mu + max(3·base_sd, 1%p)` 를 연속 3 bin 초과)을 같이 냈다. 이쪽은 세 런이
일관된다: **+98.9 / +99.8 / +104.9 초, 전부 step 9~10 (4.9→3.3 Mbit/s)**.

이 값은 물리적으로도 맞다. search 응답 4474 B = 35,792 bit 이므로 직렬화
시간은 4.9 Mbit/s 에서 7.2 ms, 3.3 Mbit/s 에서 10.9 ms 다. `site_s3` 의 search
`corrected` p50 이 30.2 ms, SLO 가 45 ms 라 여유가 약 15 ms 인데, 바로 그
구간에서 꼬리가 SLO 를 넘기 시작한다.

**주의**: `T_dep` 은 이 램프 기울기(10초마다 1.673 Mbit/s)에 묶인 값이다.
기울기가 다르면 시간도 달라진다. 기울기와 무관한 양은 **"전송률 4.9→3.3
Mbit/s 에서 깨진다"** 쪽이다. `h` 를 시간으로 쓸지 임계 전송률로 쓸지는
사람이 정할 문제다.

### 4.6 Jaeger 에 애플리케이션 스팬이 하나도 없다 → 표 5 를 대체 구성
`/api/services` 가 `jaeger-all-in-one` 하나만 반환한다. 원인을 확인했다:

- 그런데 **jaeger 컨테이너가 UDP 를 하나도 listen 하지 않는다.** 컨테이너 안

  있다. `jaegertracing/all-in-one:latest` 가 v2 로 올라가면서 레거시

따라서 "스팬 수 / 서비스별 duration 상위 3개"는 **이 데이터로는 만들 수 없다.**
표 5 는 (a) DSB 소스 정적 판독으로 호출 구조를, (b) 유휴 단발 요청 실측과
memcached stats 로 시간·부피를 채웠다. **부하는 걸지 않았다** (엔드포인트당

## 5. `f_c` 를 논문에 쓸 때 붙여야 할 단서

측정된 `f_c` 는 **캐시가 사실상 100% 적중하는 상태**의 값이다.

| memcached | curr_items | 적중률 | 총 미스 |
| --- | ---: | ---: | ---: |
| profile | 27 | **100.000%** | 27 (44시간 누적) |
| rate | 5 | **100.000%** | 5 (44시간 누적) |
| reserve | 2 | 3.962% | 856,260,716 |

lat/lon 이 고정이라 geo 가 항상 같은 소수의 호텔을 돌려주고, profile/rate 워킹셋이
각각 27·5 개로 고정된다. 워밍업 이후 이 두 캐시는 미스가 나지 않는다.
모든 정책·사이트가 같은 조건이므로 **비교 자체는 오염되지 않지만**, `f_c`
절대값을 "호텔예약 서비스의 서버 처리시간"으로 일반화하면 과소평가다.

`reserve` memcached 만 96% 미스인데, 이건 search 경로에 있다
(`searchHandler` → `reservation.CheckAvailability`). 읽는 키는
`hotelId_outDate_outDate` 인데 쓰는 키는 `hotelId_cap` 이라(서로 다른 GetMulti)
날짜 키는 사실상 영구 미스이고 매번 MongoDB 로 간다. `curr_items=2`,
`evictions=0` 이 이를 뒷받침한다.

## 6. `rate` 업스트림 버그 — 확인했고, 예상과는 형태가 다르다

`services/rate/server.go:142` 가 `collection.Find(ctx, bson.D{})` 로 **hotelId
필터 없이 inventory 전체를 스캔**하는 것은 사실이다(인수인계 §5.2 와 일치).

다만 이 스캔은 **memcached 미스 때만** 돌고, rate 캐시는 미스가 총 5회뿐이다.
대신 **그 전체 스캔 결과가 캐시에 그대로 구워져 있다**:

- rate 캐시 키는 `1`, `3`, `6` … 5개인데 **각 키의 값이 10,685 B / 56개 rate
  plan** 이다. 키 `6` 안에 `hotelId:"1"` 이 들어 있다 — 전체 인벤토리 덤프다.
- 그래서 search 1건은 rate 에서 5키 × 10.7 KB ≈ **53.7 KB** 를 읽고
  **280개(5×56) rate plan 을 JSON 언마샬**한다.
- `services/search/server.go:165-168` 에는 중복 제거가 없다. `res.HotelIds` 에
  rate plan 마다 하나씩 들어가 **280개(중복 포함) hotelId** 가 하류로 흐르고,
  그대로 `CheckAvailability` 로 넘어간다.
- 검증: `cmd_get` 비 profile/rate = 47.8M/8.71M = 5.49. 믹스(reserve 1 : search
  1.5 : recommend 2)에서 profile 41회 / rate 1.5k 회를 풀면 k≈5 로 일치한다.

즉 `f_c` 의 search > reserve 격차 원인은 "매 요청마다 mongo 전체 스캔"이 아니라
**전체 스캔 결과가 캐시된 뒤의 대용량 페이로드 전송 + 파싱 + 중복 없는 280건
하류 확산**이다. 스팬이 없어 `rate` 단독 duration 은 직접 못 쟀다.

## 7. 사람이 판단해야 하는 항목 (요약)

1. `bl_loc` 를 그림에 남길지 (모든 조건에서 100%라 정보량이 거의 없다).
2. `h` 를 시간(≈100초)으로 쓸지 임계 전송률(4.9→3.3 Mbit/s)로 쓸지.
3. `B_ramp_bl_rr` 을 그대로 실을지, S1 상태 교란요인을 각주로 달지, 재측정할지.
4. 서버 교란 시나리오를 이대로 쓸지 — 비교군 런에서는 S3 몫이 작아 열화가
   사이트 간 상시 격차에 묻힌다. 강도를 올리거나 S1 을 안정 용량 안으로
   넣어야 "반응 지연"을 볼 수 있을 가능성이 있다.
5. Jaeger 스팬이 필요하면 collector 설정을 고쳐야 한다(예: OTLP 4317 로 전환).
   **이번 작업에서는 테스트베드를 건드리지 않았다.**
6. `f_c` 에 붙일 캐시 단서 문구.
